# Нагрузочные тесты совместной работы

Сколько досок и участников выдерживает одна установка CoDraw, во что она упирается первой и какие ресурсы ей дать.
Цифры ниже получены 10 октября 2026 года в облачном контейнере, где делалась эта работа, — не на сервере установки.
Их стоит читать как соотношения («сколько участников на одно ядро `collab`», «что упирается первым»), а свои
абсолютные цифры оператор получает той же командой на своём сервере.

## Как запустить

Нагрузочный клиент — подпроект `load/`. Он нагружает уже запущенный стек через адрес приложения, как браузеры:

```bash
# стек из docker-compose.prod.yml; все участники нагрузки — гости с одного адреса, поэтому предел гостей поднят
CODRAW_LIMITS_GUESTS_PER_ADDRESS_PER_HOUR=1000000 docker compose -f docker-compose.prod.yml --env-file .env.prod up -d --wait
pnpm install
pnpm load                       # все сценарии против http://localhost:8080, около 25 минут
pnpm load --help                # шаги, длительность, частота правок и курсоров, цель
```

Отчёт печатается и сохраняется в `load/results/` (Markdown и JSON). Вручную его можно получить и в GitHub Actions:
workflow **Load** (`Actions → Load → Run workflow`) собирает образы коммита, поднимает стек на раннере и прикладывает
отчёт к запуску. На каждом пуше нагрузка не запускается. Против рабочей установки её не запускают: клиент создаёт
гостей и доски (доски удаляет после каждого шага, гостей убирает обычная уборка гостей).

Без Docker клиент работает по одному адресу приложения (например, `http://localhost:5173` с `pnpm dev:*`), метрики
`collab` читает по `--collab-metrics-url http://localhost:1234/metrics`, а сценарий `reconnect` пропускает.

## Что делает участник нагрузки

Каждый участник — отдельный гость и проходит тот же путь, что приложение, без обходов:

1. `GET /api/me` за CSRF-cookie, `POST /api/guest` — вход «Продолжить без входа».
2. Первый участник доски создаёт её (`POST /api/boards`), остальные открывают по ссылке (`GET /api/boards/{id}`).
3. `@hocuspocus/provider` подключается к `/collab`; перед каждым подключением, в том числе после разрыва, участник
   берёт токен `POST /api/boards/{id}/collab-token`. `collab` проверяет подпись токена и спрашивает доступ у `backend`.
4. Участник создаёт до 20 прямоугольников на первой странице в модели документа приложения и дальше двигает их, в
   среднем раз в 3 с, и двигает курсор через awareness в среднем раз в 250 мс. Интервалы случайные (экспоненциальные),
   чтобы участники не действовали в такт. Курсор в приложении уходит до 20 раз в секунду, пока мышь движется, —
   250 мс в среднем соответствуют участнику, который то двигает мышь, то смотрит.

Задержка доставки — время от правки (или движения курсора) у одного участника до её прихода к каждому другому
участнику доски; отметка времени едет в самой правке. Все участники живут в одном процессе клиента, поэтому сдвиг
часов машин в задержку не попадает. Клиент делит участников между потоками (по числу ядер, не больше 8) и меряет
задержку цикла событий каждого: если p99 больше 50 мс, отчёт предупреждает, что клиент не успевал и задержки шага
включают его собственную очередь.

Шаг — 10 с разгона и 60 с замера. Шаг **выдержан**, если p95 доставки правки ≤ 200 мс, доставлено не меньше 99,9 %
правок и нет отказов во входе, токене, подключении и сохранении документа. **Предел** — последний выдержанный шаг.

## Сценарии

| Сценарий | Что проверяет |
|---|---|
| `boards` | обычная нагрузка: много досок по 3 участника, шаги по числу досок |
| `crowd` | воркшоп или показ: одна доска, шаги по числу участников; каждый курсор уходит всем |
| `large` | доски, заполненные до 90 % предела размера документа (14,4 МиБ из 16 МиБ), по 3 участника, которые их открывают и правят; рядом в том же окне правят 20 обычных «соседних» досок по 3 участника (`--large-neighbours`), их задержки — отдельной строкой |
| `reconnect` | `docker restart collab` под нагрузкой: все переподключаются с новыми токенами, правки без связи доходят до всех |

## Стенд

| | |
|---|---|
| Машина | облачный контейнер: 4 vCPU Intel Xeon 2,1 ГГц, 16 ГБ памяти, Linux 6.18, Docker 29.8 |
| Стек | `docker-compose.prod.yml` целиком: nginx (`frontend`), `backend` (JRE 25), `collab` (Node.js 24.21), PostgreSQL 18.6, RustFS; без ограничений процессора и памяти контейнеров |
| Образы | финальные стадии `backend/Dockerfile`, `collab/Dockerfile`, `frontend/Dockerfile` этого коммита; стадии сборки выполнены на той же машине (реестр образов из контейнера недоступен) |
| Настройки | по умолчанию, кроме `CODRAW_LIMITS_GUESTS_PER_ADDRESS_PER_HOUR=1000000`; окно рассылки `collab` — 0 |
| Клиент | на той же машине, 4 потока |

Клиент и стек делят 4 ядра, и под большой нагрузкой клиент забирает их часть у nginx, `backend` и PostgreSQL. На
сервере, где работает только стек, результаты будут не хуже.

--reconnect-boards 200` против стека из `main` (до) и с сохранением документов в потоке `collab`
([ADR-0012](adr/0012-document-stores.md), issue #174, после). Клиент — из этого изменения, со строкой соседних досок;
задержка цикла событий клиента — не больше 47 мс по p99 ни на одном шаге.

Во всех шагах `boards` и `large` доставлено 100 % правок, отказов не было. В `reconnect` все 600 участников вернулись
(до — за 6,0–6,5 с, после — за 5,5 с), правки, сделанные без связи, дошли до всех.

¹ Время сохранения теперь включает кодирование в потоке сохранений: раньше оно шло в главном потоке до начала замера.
Сохранений на шаге больше, чем в строке без соседей: правят и соседние доски.

² Два прогона `main`: задержки правок во время перезапуска сильно разнятся от прогона к прогону.

**До.** Сохранение доски 14,4 МиБ занимало главный поток `collab`: кодирование, текст для поиска, отправка тела
`backend`. Правки и больших, и соседних досок ждали: p99 — 110 мс у обеих групп при медиане 1–2 мс, p95 соседних досок —
24 мс против 4 мс на тех же маленьких досках без больших рядом.

**После.** p95 доставки правки на досках у предела размера — 3,0 мс, у соседних — 2,3 мс, p99 — 3,5 и 4,6 мс: как на
маленьких досках без больших рядом (`boards` 50 × 3 — 2,9 / 5,9 мс). Критерии issue #174 (не больше маленьких досок
плюс 20 мс, сохранение большой доски не задерживает соседние) выполнены. На многих досках главный поток тоже
освободился: на 200 × 3 p95 упал с 68 до 17 мс.

**Чем оплачено.**

- Память. Поток сохранений держит копию каждого открытого документа, и у него своя куча V8. На 100–200 обычных досках
  `collab` занял на 170–230 МиБ больше. С тремя досками по 14,4 МиБ пик — 0,9 ГБ вместо 0,3–0,5 ГБ: около 200 МиБ на
  открытую доску у предела вместо 100–130. Это пик резидентной памяти: копия, буферы закодированных состояний и мусор
  кучи потока до сборки.
- Процессор. `process_cpu_seconds_total` теперь считает оба потока, и на 200 × 3 процесс занят на 76 % ядра против
  62 %. Это второе применение каждой правки и кодирование в потоке сохранений, на другом ядре. Предел одной установки
  задаёт главный поток, и он стал свободнее. Правило `CodrawCollabBusy` считает процессор всего процесса, поэтому теперь
  срабатывает с запасом.
- Открытие большой доски по-прежнему применяет состояние и отвечает новому участнику в главном потоке: вход на
  `large` — 1,6–2,4 с.

## Предел одной установки

**Один процесс `collab` на ядре Xeon 2,1 ГГц держит p95 доставки правки ≤ 200 мс до 300 одновременно открытых досок
по 3 активных участника — 900 участников; на 400 досках (1200 участников) p95 — 315 мс.** Доска из 100 активных
участников держит цель (p95 88 мс, `collab` — 39 % ядра); с окном рассылки 30 мс — и из 150.

Первым упирается процессор `collab`: это один процесс Node.js, и все документы, соединения и курсоры проходят через
его единственный цикл событий. После ~75 % ядра p95 растёт быстро: 18 мс при 73 %, 45 мс при 80 %, 83 мс при 87 %,
315 мс при 89–99 %. `backend` и PostgreSQL при этом заняты на 10–15 % ядра, сохранения документов успешны и укладываются
в десятки миллисекунд, пока `collab` не перегружен.

Нагрузку участника задают курсоры: на 900 участниках `collab` принимает ~3600 сообщений awareness в секунду и
рассылает их соседям, против ~300 правок. Если участники в среднем двигают курсор реже, предел выше.

## Узкие места

### Исправлены в этом изменении

**Временный `Y.Doc` на каждое сообщение awareness.** Профиль `collab` под нагрузкой 150 × 3 (`node --cpu-prof`)
показал, что 16 % всего времени процесса — 27 % занятого — уходит в `crypto.getRandomValues`. Hocuspocus 4.7.0
(последняя версия) на каждое сообщение awareness создаёт временные `Y.Doc` и `Awareness` для хука
`beforeHandleAwareness`, а `Y.Doc` без `guid` создаёт его через `uuidv4` — 31 обращение к системному генератору
случайных чисел. Патч `patches/@hocuspocus__server@4.7.0.patch` даёт временному документу постоянный `guid`; хуки и
поведение те же. На 150 × 3 (`collab` вне контейнера, остальное — тот же стек) ЦП `collab` упал с 77 % до 57 % ядра, p95
правки — с 15 до 5 мс; на стеке 100 × 3 — с 70 % до 49 % и с 30 до 5 мс (до исправления замер шёл 20 с, после — 60 с). При обновлении Hocuspocus pnpm потребует
перенести патч или убрать его, если исправят в самом Hocuspocus.

**Соединения nginx.** На шаге 300 × 3 до исправления 167 из 900 участников не смогли подключиться за 120 с, а nginx
писал `1024 worker_connections are not enough`. Базовый образ nginx даёт 1024 соединения рабочему процессу при
процессе на ядро, а каждый участник держит два соединения — от браузера и к `collab`; соединения распределяются по
процессам неравномерно, так что предел наступал раньше 4 × 512 участников, а на сервере с одним ядром был бы около
500 участников. Образ `frontend` теперь даёт 4096 соединений процессу; после этого отказов во входе нет ни на одном
шаге.

**Окно рассылки** — новая настройка `CODRAW_COLLAB_BROADCAST_DELAY_MS` (см. выше и [docs/deploy.md](deploy.md)).

**Оповещение.** Правило Prometheus `CodrawCollabBusy` срабатывает, когда `collab` 10 минут занимает больше 80 % ядра, —
до того, как правки начнут доходить с заметной задержкой.

### Заведены отдельно

- [#173](https://github.com/TheScarletArrow/codraw/issues/173) — несколько экземпляров `collab`: предел одного
  процесса — одно ядро, больше ядер одной установке не помогают.
- [#174](https://github.com/TheScarletArrow/codraw/issues/174) — большие доски: каждое сохранение кодировало и
  отправляло в `backend` документ целиком в главном потоке `collab` (p95 сохранения 457 мс на 14,4 МиБ), и на это
  время останавливалась доставка правок (p95 правки 106 мс при медиане 2,4 мс). Исправлено: документы сохраняет
  отдельный поток `collab`, см. «[Сохранение больших досок](#сохранение-больших-досок-вне-главного-потока)».

## Рекомендации по ресурсам и пределам

| Одновременно открытых досок (по 2–3 активных участника) | Сервер |
|---|---|
| до 100 | 2 vCPU, 4 ГБ памяти |
| до 200 | 2–4 vCPU, 4 ГБ памяти |
| до 300 | 4 vCPU, 8 ГБ памяти; ближе к пределу одного процесса `collab` |
| больше 300 | одного процесса `collab` не хватит, см. #173 |

- **Процессор.** Правки и курсоры всех досок `collab` обслуживает один поток — одно ядро, сколько бы их ни было; поток
  сохранений занимает часть другого; держите процесс ниже ~70 % ядра в часы пик
  (`rate(process_cpu_seconds_total{job="collab"}[5m])`, правило `CodrawCollabBusy`). Остальные ядра нужны nginx,
  `backend` и PostgreSQL: на 300 досках они вместе занимали около 60 % ядра (nginx — 36 %, `backend` — 12 %,
  PostgreSQL — 11 %). Ядро медленнее 2,1 ГГц даст
  пропорционально меньше досок.
- **Память.** `collab` — 250–400 МиБ на 100–200 досок, ~650 МиБ на 300–400 и плюс около 2–3 размеров каждого
  открытого большого документа (три доски по 14,4 МиБ — 384 МиБ). С потоком сохранений (#174) — на 170–230 МиБ больше
  на 100–200 досках и около 200 МиБ на каждую открытую доску у предела (три доски по 14,4 МиБ — пик 0,9 ГБ);
  заложите `collab` 1,5 ГБ. `backend` — JVM, которая
  берёт до 75 % памяти контейнера: на стенде без ограничений она заняла 0,9–1,1 ГБ, на сервере с 2 ГБ ей хватает
  меньшего. PostgreSQL — 130–200 МиБ. Итого 2 ГБ из раздела «Что нужно» [docs/deploy.md](deploy.md) — минимум для
  десятков досок, 4 ГБ — для сотен.
- **Многолюдные доски.** Доска из 100 активных участников держит цель при окне 0. Если такие доски — обычное дело
  (воркшопы, показы на всю компанию), задайте `CODRAW_COLLAB_BROADCAST_DELAY_MS=20`–`30`: это вдвое снижает процессор
  `collab` на них ценой 20–30 мс задержки каждой правки. Если установка — это в основном много маленьких досок,
  оставьте 0.
- **Размер документа.** Предел 16 МиБ (`DOCUMENT_SIZE_LIMIT_BYTES`) работает: доска у предела открывается за ~1,5–2 с и
  сохраняется за ~0,3–0,5 с в отдельном потоке, не задерживая правки ни её, ни остальных досок. Ограничивает её память
  `collab`: около 200 МиБ на каждую открытую доску у предела. Если таких досок открыто много, а памяти мало,
  предел можно опустить до 8 МиБ.
- **Перезапуск `collab`** — обновление или сбой — обходится участникам в несколько секунд: 600 участников
  вернулись за 7 с без потери правок. Обновляйте `collab` вне часов пик, но отдельного окна обслуживания не нужно.

## Как читать отчёт клиента

| Столбец | Что |
|---|---|
| Вход p95 | от создания участника до синхронизации доски; участники шага подключаются одновременно, так что это время наплыва, а не одного входа |
| Правка, Курсор | задержка доставки другому участнику доски |
| Доставлено | доля правок, дошедших до всех других участников их досок |
| Разрывы | соединения, закрывшиеся во время шага |
| Сохранений, Сохранение p95 | сохранения документов `collab` в `backend` за шаг и их длительность — кодирование в потоке сохранений и запись в `backend` — по гистограмме `codraw_collab_store_duration_seconds` |
| ЦП, память | `docker stats` контейнеров (без Docker — метрики процесса `collab`) |
