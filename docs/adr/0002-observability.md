# ADR-0002: Наблюдаемость

- **Статус:** принято
- **Дата:** 2026-10-05

## Контекст

ADR-0001 выбрал стек приложения, но не то, как следить за ним на сервере. Перед запуском нужно видеть нагрузку,
ошибки, работу пределов и уборки гостей, узнавать о поломке раньше пользователей и разбирать журналы без регулярных
выражений. Сервисов два — `backend` на Spring Boot и `collab` на Node.js, — плюс nginx и PostgreSQL в одном
Docker Compose.

## Решение

| Что | Выбор |
|---|---|
| Метрики | формат Prometheus; `backend` — Micrometer (`micrometer-registry-prometheus`) через Actuator, `collab` — `prom-client` |
| Сбор и правила | Prometheus в профиле `monitoring` стека, правила оповещений в репозитории |
| Журналы | JSON по строке на событие в формате ECS: `backend` — встроенное структурированное журналирование Spring Boot, `collab` — свой модуль с теми же полями |

## Обоснование

- Prometheus — стандарт для контейнеров: его читает любой облачный мониторинг, а Spring Boot и Node.js отдают его
  готовыми библиотеками, без своего кода сбора.
- ECS понимают Elasticsearch, Loki, облачные журналы; Spring Boot пишет его сам, и у `collab` те же поля.

Отклонённые альтернативы:

- **OpenTelemetry (OTLP) с коллектором** — метрики, журналы и трассировка одним протоколом, но ещё один сервис в
  стеке и настройка экспорта ради того же результата. Переход возможен позже: Micrometer умеет OTLP.
- **Свои эндпоинты статистики в JSON** — меньше зависимостей, но ни правил, ни истории, ни совместимости с
  мониторингами.

## Последствия

- Новые зависимости: `micrometer-registry-prometheus` в `backend` и `prom-client` в `collab`.
- Метрики открыты без входа внутри сети стека; снаружи их закрывает nginx. Это нужно сохранять при изменении
  прокси.
- Доставка оповещений, дашборды и хранение журналов — за тем, кто разворачивает, и в отдельных решениях.
