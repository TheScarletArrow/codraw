# ADR-0010: Корпоративный вход через OpenID Connect

- **Статус:** принято
- **Дата:** 2026-10-10

## Контекст

В CoDraw входят через GitHub, Google или гостем (ADR-0001). Компании, которые ставят CoDraw у себя, пускают
сотрудников через собственный провайдер удостоверений — Keycloak, Microsoft Entra ID, Okta, ADFS — и не могут требовать
личных учётных записей GitHub или Google, а гостевой вход в закрытой установке не нужен (issue #158). Провайдеры у всех
разные, поэтому вход должен подключаться настройками установки, а не кодом. Учётные записи пользователей CoDraw уже
держат доски, участие и историю, поэтому связь с внешним пользователем должна быть устойчивой: почта и имя у провайдера
меняются, а провайдеров в установке может быть несколько.

## Решение

| Что | Выбор |
|---|---|
| Протокол | OpenID Connect, код авторизации с проверкой ID-токена — `spring-boot-starter-security-oauth2-client`, который уже в стеке |
| Настройка | `codraw.auth.oidc.<id>`: issuer, client id и secret, scope, название кнопки, ограничения, выход у провайдера; провайдер без issuer или client id выключен |
| Метаданные | `<issuer>/.well-known/openid-configuration` при первом входе, удача кэшируется до перезапуска; недоступный провайдер не мешает старту `backend`, а вход через него возвращает на страницу входа с ошибкой |
| Связь учётной записи | пара `iss` + `sub` из проверенного ID-токена в `users.provider` (`oidc:<iss>`) и `users.provider_user_id`; почта и имя не участвуют |
| Данные | имя (`name`, `preferred_username`, `email`, `sub`) и аватар (`picture`) хранятся; почта и группы только сверяются с ограничениями при входе |
| Ограничения | домены почты (точное совпадение, `email_verified` не `false`) и группы из claim (по умолчанию `groups`); отказ не создаёт учётную запись |
| Закрытая установка | GitHub и Google включены, только если задано их OAuth-приложение; гостевой вход выключает `codraw.guests.enabled=false` |
| Выход | по желанию — RP-initiated logout: браузер уходит на `end_session_endpoint` с `id_token_hint` и возвращается на страницу входа |

## Обоснование

- OIDC говорят все распространённые корпоративные провайдеры, включая ADFS и Entra ID, а Spring Security проверяет
  подпись, `iss`, `aud`, срок и `nonce` ID-токена сам. SAML 2.0 — отдельная библиотека (OpenSAML), сертификаты и XML;
  его стоит добавлять, только если появится установка, где OIDC недоступен.
- `iss` + `sub` — единственная пара, которую OIDC обещает не менять и не переиспользовать. Связь по почте отдала бы
  чужую учётную запись тому, кому администратор выдал освободившийся адрес, и ломалась бы при смене почты; связь по id
  провайдера в настройках ломалась бы при переименовании. Пара укладывается в уже уникальные `users(provider,
  provider_user_id)`, поэтому миграции нет; префикс `oidc:` отделяет её от `github`, `google` и `guest`.
- Ленивые метаданные, а не `issuer-uri` Spring Boot: тот читает их при старте, и недоступный провайдер не дал бы
  запустить `backend` даже для GitHub и гостей.
- Почту не хранить: CoDraw она нужна только для писем, а там пользователь подтверждает адрес сам (ADR-0008).
  Ограничение по домену сверяет её при каждом входе, этого достаточно.
- Выход у провайдера выключен по умолчанию: адрес возврата нужно сначала разрешить у провайдера, иначе «Выйти» упрётся в
  его ошибку.

Отклонённые альтернативы:

- **SAML 2.0** — новая библиотека и протокол ради провайдеров, которые и так говорят OIDC.
- **Связь по почте** и **слияние учётных записей разных провайдеров** — риск захвата учётной записи; слияние, если
  понадобится, — явное действие пользователя, вошедшего в обе.
- **Провайдеры в `spring.security.oauth2.client.*`** — оператору пришлось бы задавать `registration` и `provider`
  отдельно, а ограничения и название кнопки всё равно жили бы в своих настройках.

## Последствия

- Смена issuer провайдера (новый адрес Keycloak, другой каталог Entra ID) создаёт новые учётные записи; доски старых
  передаются вручную. Это написано в `docs/deploy.md`.
- Entra ID поддерживается с issuer конкретного каталога (`https://login.microsoftonline.com/<tenant>/v2.0`), а не
  `/common`: метаданные `/common` называют issuer шаблоном, и проверка совпадения не проходит.
- Сеанс корпоративного пользователя хранит его ID-токен — для `id_token_hint` при выходе у провайдера.
- Интеграционный тест входит через настоящий Keycloak в Testcontainers (образ только для тестов).
