# ADR-0016: Автоматическая выкатка из CI по SSH

- **Статус:** принято
- **Дата:** 2026-10-14

## Контекст

CoDraw разворачивается на одном сервере из `docker-compose.prod.yml` и `.env.prod` (`docs/deploy.md`). CI при каждом
пуше собирает образы, поднимает из них стек и проверяет его; в `main` публикует образы с тегом коммита, а `latest`
ставит после всех проверок. До сервера образы доходили руками: `pull`, `up -d --wait`, резервная копия перед
изменением схемы и новый `docker-compose.prod.yml`, если он изменился. Сервер отставал от `main`, а неудачная выкатка
откатывалась вручную.

## Решение

| Что | Выбор |
|---|---|
| Где | задача `deploy` в `ci.yml` после `release`, только для `main`, в GitHub Environment `production` |
| Как | SSH на сервер с ключом из секретов Environment, `StrictHostKeyChecking=yes` и `known_hosts` из секрета |
| Очередь | `concurrency: production` без отмены: одна выкатка за раз, ждущую вытесняет более новая |
| Что выкатывается | образы коммита и его `docker-compose.prod.yml`, `deploy/prometheus`, `deploy/alertmanager`, `deploy/cd`; `.env.prod` и `docker-compose.override.yml` — оператора |
| Скрипт | `deploy/cd/codraw-deploy` на сервере: `compose config` с `.env.prod`, образы, резервная копия, переключение файлов, `up --wait`, откат, удаление старых образов |
| Реестр | токен задачи (`packages: read`) через stdin во временную конфигурацию Docker |
| Не настроено | без `CODRAW_DEPLOY_HOST` задача проходит с пометкой |
| Проверка | `codraw-deploy.test.sh` с поддельным `docker` и `check-deploy.sh` против стека задачи `images`: выкатка, отказ, откат |

## Обоснование

- Push из Actions виден там же, где проверки: зелёная или красная задача, журнал выкатки и отката у коммита. Pull на
  сервере (таймер или Watchtower) не нуждается во входящем SSH, но результат не виден в GitHub, файлы стека так не
  обновить, а Watchtower пересоздаёт контейнеры по одному, без резервной копии, `--wait` и отката.
- Self-hosted runner на сервере не требует SSH, но держит на продакшене процесс с доступом к сокету Docker, который
  выполняет задачи из репозитория и который нужно обновлять и охранять.
- Всё, что может упасть, проверяется до остановки контейнеров: конфигурация с `.env.prod`, образы, резервная копия.
  Откат возвращает и файлы, а не только версию образов: иначе прежний образ мог бы встретить чужую конфигурацию.
- Токен задачи живёт только во временной конфигурации Docker на время скачивания: учётные данные сервера не
  меняются, постоянного токена на сервере нет. В stdin, а не в командной строке: аргументы видны в списке процессов.
- Скрипт — функция, вызванная последней строкой: bash прочтёт файл целиком, и выкатка новой версии самого скрипта не
  подменит его на ходу.
- Журналы контейнеров в задачу не пишутся: журналы Actions видят все, у кого есть доступ к репозиторию, а в журналах
  продакшена — адреса и имена пользователей.

Отклонённые альтернативы:

- **Watchtower / таймер systemd** — см. выше.
- **Self-hosted runner** — см. выше.
- **Kubernetes, blue-green, выкатка без простоя** — установка — один сервер, а `collab` держит документы в памяти;
  перезапуск даёт десятки секунд «Нет связи», которые клиенты переживают сами.

## Последствия

- Ключ SSH в секретах даёт управление Docker на сервере, то есть права root: пользователь и ключ — отдельные, только
  для выкатки; Environment можно защитить подтверждением и веткой `main`.
- Откатываются файлы и образы, но не схема базы: прежний `backend` пропускает незнакомые миграции, несовместимое
  изменение схемы откатывается U-скриптами вручную.
- Откат уже выкаченной версии — перезапуск задачи `deploy` у нужного коммита; `latest` при этом не меняется.
- Второй стенд (staging) добавляется вторым Environment той же задачи.
