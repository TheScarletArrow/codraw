# ADR-0015: Вход через Яндекс ID и VK ID

- **Статус:** принято
- **Дата:** 2026-10-13

## Контекст

В CoDraw входят через GitHub, Google, корпоративный провайдер OpenID Connect (ADR-0011) или гостем. У российских
пользователей основные учётные записи — Яндекс ID и VK ID, а GitHub и Google у многих нет или вход через них работает
ненадёжно. Установке для российской аудитории нужен вход через эти сервисы, и включать его оператор должен
настройками, как GitHub и Google.

Оба провайдера — OAuth, но не OpenID Connect с метаданными, поэтому корпоративный вход ADR-0011 их не подключает:

- Яндекс ID — OAuth 2.0 без ID-токена; профиль `login.yandex.ru/info` принимает токен в схеме `Authorization: OAuth`.
- VK ID — OAuth 2.1 на `id.vk.ru` (ВКонтакте перевела авторизацию на домен `vk.ru`) с обязательным PKCE. Обратный
  вызов несёт `device_id`, без которого код не обменять; `state` — только буквы, цифры, `_` и `-`; профиль —
  `POST /oauth2/user_info` с `client_id`, внутри поля `user`.

## Решение

| Что | Выбор |
|---|---|
| Настройка | регистрации `yandex` и `vk` Spring Boot в `application.yaml`; оператор задаёт `YANDEX_CLIENT_ID`, `YANDEX_CLIENT_SECRET` и `VK_CLIENT_ID`, без них провайдер выключен (`not-configured`) |
| Яндекс ID | код авторизации, секрет в теле обмена (`client_secret_post`), права `login:info` и `login:avatar`, профиль с `Authorization: OAuth` |
| VK ID | публичный клиент (`none`): PKCE S256 без секрета приложения, право `vkid.personal_info`; `device_id` из обратного вызова и `state` в обмене кода, профиль `POST` с `client_id` |
| `state` | 32 случайных байта в Base64 URL без `=` для всех провайдеров |
| Учётная запись | `users.provider` = `yandex` или `vk`, `provider_user_id` — `id` Яндекса или `user_id` VK; миграции нет |
| Данные | имя и аватар хранятся; почта не запрашивается; логин, пол и дата рождения приходят с профилем и не хранятся |
| Администраторы | `yandex:<id>` и `vk:<user_id>` в `CODRAW_ADMINS` |

## Обоснование

- Регистрации Spring Boot — тот же путь, что у GitHub и Google: оператор задаёт только id и секрет, а адреса
  провайдеров остаются настройками, которые можно переопределить без нового образа (VK уже однажды сменил домен).
- Права Яндекса перечислены явно: без `scope` Яндекс выдал бы все права приложения, в том числе почту, если оператор её
  отметил, а CoDraw почта от провайдеров не нужна (ADR-0008).
- VK ID как публичный клиент: секрет приложения при обмене кода не нужен (веб-SDK VK ID меняет код в браузере),
  защиту кода даёт PKCE, а оператору на одну переменную и один секрет меньше. Spring Security сам добавляет PKCE
  клиенту без секрета.
- Особенности VK ID закрыты точечными расширениями Spring Security, без своей реализации OAuth: customizer запроса
  авторизации (`state`), конвертер параметров обмена кода (`device_id`, `state`) и конвертеры запроса профиля.
  `device_id` берётся из запроса обратного вызова — обмен кода идёт в нём же.
- Связь по id провайдера, как у GitHub: оба обещают, что id пользователя не меняется, а логин, имя и почта меняются.

Отклонённые альтернативы:

- **Подключать как корпоративных провайдеров OIDC** — у Яндекс ID нет ID-токена, а VK ID требует `device_id` и
  отдаёт профиль не по стандарту userinfo.
- **Секрет приложения VK ID при обмене кода** — не нужен VK ID и только добавил бы оператору секрет.
- **Госуслуги (ЕСИА), Сбер ID, T-ID** — требуют договора с владельцем сервиса или регистрации в ЕСИА, сертификатов
  и подписи запросов (в ЕСИА — ГОСТ); это работа под конкретную установку, а не настройка. Если такой провайдер говорит
  OIDC, его подключают как корпоративного (ADR-0011).
- **Отдельные кнопки Mail и Одноклассников** — VK ID документирует их для своего SDK; их можно добавить позже тем же
  приложением VK ID.

## Последствия

- Пользователь, вошедший через Яндекс ID и через VK ID, получает две учётные записи, как с GitHub и Google.
- «Выйти» завершает только сеанс CoDraw; сеанс у Яндекса или VK остаётся.
- Политика конфиденциальности называет Яндекс ID и VK ID и что от них приходит, а условия и подсказки гостю больше не
  называют конкретных провайдеров.
- Тесты входят полным кодом авторизации через поддельные серверы провайдеров (`FakeSignInProviders`), которые
  проверяют запросы так, как их проверяют провайдеры; с настоящими приложениями вход проверяется по `docs/deploy.md`.
- Неудачный вход через провайдера пишет причину в журнал `backend`.
