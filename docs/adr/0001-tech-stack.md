# ADR-0001: Технологический стек

- **Статус:** предложено
- **Дата:** 2026-10-03

## Контекст

CoDraw — браузерный редактор диаграмм (аналог draw.io) с совместным редактированием в реальном времени.

Основные технические сложности:

1. **Синхронизация состояния** между клиентами: конкурентные правки одного элемента, офлайн-правки,
   undo/redo для каждого участника отдельно, присутствие (курсоры, выделения).
2. **Интерактивный холст**: зум, панорамирование, выделение, перетаскивание, коннекторы с привязкой
   к фигурам, редактирование текста прямо на холсте.

Требования: диаграммы до сотен элементов; полноценный импорт и экспорт `.drawio`.

Основная экспертиза команды — Java/Kotlin. Фронтенд в любом случае будет на TypeScript: холст живёт
в браузере, а нужные библиотеки (CRDT, движки диаграмм) существуют только в JS-экосистеме.

## Решение

| Слой               | Выбор                                                          |
|--------------------|----------------------------------------------------------------|
| Frontend           | TypeScript, React, Vite                                        |
| Холст диаграмм     | maxGraph (`@maxgraph/core`)                                    |
| Формат файлов      | `.drawio` (mxGraph XML) — импорт и экспорт                     |
| UI                 | Tailwind CSS, shadcn/ui                                        |
| Состояние          | Yjs — документ; Zustand — локальное UI-состояние; TanStack Query — REST |
| Синхронизация      | Yjs (CRDT) + awareness поверх WebSocket                        |
| Collab-сервер      | Hocuspocus (Node.js, TypeScript)                               |
| Backend API        | Kotlin, Spring Boot 4, JDK 25, Gradle (Kotlin DSL)             |
| БД                 | PostgreSQL, Flyway, Spring Data JDBC                           |
| Файлы              | S3-совместимое хранилище (MinIO локально), после MVP           |
| Аутентификация     | Вход через GitHub/Google, JWT от backend; Keycloak — при необходимости SSO |
| Масштабирование    | Redis pub/sub между инстансами collab-сервера (когда понадобится) |
| Контракт API       | OpenAPI (springdoc) → сгенерированный TS-клиент                |
| Тесты              | JUnit 5, Testcontainers; Vitest; Playwright (e2e, в т.ч. несколько клиентов) |
| Инфраструктура     | Docker, Docker Compose, GitHub Actions                         |

### Архитектура

```
┌──────────────────────┐   WebSocket (Yjs sync + awareness)   ┌──────────────────┐
│  Frontend            │ ───────────────────────────────────▶ │  collab          │
│  React + maxGraph    │                                      │  (Hocuspocus)    │
│  Yjs Doc (истина)    │                                      └────────┬─────────┘
│  y-indexeddb         │                                               │ внутренний API:
└──────────┬───────────┘                                               │ права, load/store
           │ REST (OpenAPI)                                            ▼
           │                                                  ┌──────────────────┐
           └────────────────────────────────────────────────▶ │  backend         │
                                                              │  Kotlin + Spring │
                                                              └────────┬─────────┘
                                                                       │
                                                           PostgreSQL · S3 · (Redis)
```

- **frontend** — редактор. Источник истины — Yjs-документ; maxGraph лишь отображает его.
- **collab** — тонкий сервис (порядка сотен строк): синхронизация Yjs, awareness, слияние и
  сохранение снапшотов. Бизнес-логики не содержит.
- **backend** — вся бизнес-логика: пользователи, рабочие пространства, доски, права и ссылки
  доступа, версии, комментарии, экспорт. Единственный владелец схемы БД (миграции Flyway).

Взаимодействие collab ↔ backend:

- `onAuthenticate` — collab проверяет JWT и запрашивает у backend права пользователя на документ.
- `onLoadDocument` / `onStoreDocument` — загрузка и сохранение снапшота документа (`bytea`) через
  внутренний API backend, а не напрямую в БД.

### Сервисы

Собственного кода — два сервиса и статика. Backend — модульный монолит; дробить его на микросервисы
незачем.

| Компонент  | Что это                                                    | Когда нужен          | Масштабирование |
|------------|------------------------------------------------------------|----------------------|-----------------|
| `frontend` | Статическая сборка Vite, раздаётся nginx                   | MVP                  | CDN / любое число копий |
| `backend`  | Kotlin + Spring Boot                                       | MVP                  | Stateless, любое число инстансов за балансировщиком |
| `collab`   | Hocuspocus                                                 | MVP                  | Stateful: >1 инстанса — Redis + sticky-маршрутизация по id документа |
| PostgreSQL | Метаданные, снапшоты и версии документов                   | MVP                  | — |
| MinIO / S3 | Картинки в диаграммах, результаты экспорта                 | Загрузка изображений | — |
| Redis      | Обмен апдейтами между инстансами `collab`                  | >1 инстанса `collab` | — |
| Keycloak   | Собственный IdP                                            | SSO / self-hosted    | — |

- Для MVP достаточно 4 контейнеров: `frontend`, `backend`, `collab`, PostgreSQL.
- nginx раздаёт фронтенд и проксирует `/api` → `backend` и `/collab` → `collab`: один origin,
  без CORS.
- Вход в MVP — через GitHub/Google средствами Spring Security (OAuth2 Client). Backend выпускает
  собственный JWT, `collab` проверяет его по публичному ключу backend (JWKS). Отдельный IdP не нужен.

### Модель документа в Yjs (набросок)

Модель повторяет модель ячеек mxGraph, то есть структуру `.drawio`:

```
Y.Doc
├── meta:  Y.Map                       { title, schemaVersion }
├── pages: Y.Map<pageId, …>            страница = <diagram>: { name, order }
└── cells:<pageId>: Y.Map<cellId, Y.Map>   ячейка = <mxCell>
      ├── parent, kind (root | layer | vertex | edge), value, order
      ├── geometry                     { x, y, width, height, points, relative, offset }
      ├── source, target
      ├── style: Y.Map                 ключ → значение
      └── attrs: Y.Map                 пользовательские свойства (<object>)
```

Ячейки страницы хранятся в отдельном Y.Map верхнего уровня: вложенный Y.Map, созданный двумя
клиентами одновременно, достаётся только одному из них, а типы верхнего уровня не конфликтуют.

- Слои, группы и контейнеры — это ячейки-родители, как в mxGraph. Импорт и экспорт сводятся
  к прямому отображению.
- Каждое свойство ячейки — отдельный ключ `Y.Map`: одновременное перемещение и смена подписи
  одной фигуры не конфликтуют.
- `style` хранится как `Y.Map`, а не строкой: одновременная смена заливки и обводки не конфликтует.
  Неизвестные ключи стиля сохраняются как есть и возвращаются при экспорте.
- `geometry` меняется целиком: перемещение и ресайз всё равно затрагивают её всю.
- `value` — строка (в draw.io подпись может быть HTML). Одновременная правка одной подписи решается
  по принципу last-writer-wins — для диаграмм это приемлемо.
- Порядок (`order`) хранится как дробный индекс (fractional indexing), чтобы одновременные
  перестановки не конфликтовали.
- Undo/redo — `Y.UndoManager` с `trackedOrigins`, ограниченный локальными изменениями.
  Встроенный undo maxGraph отключается.

## Обоснование

### Синхронизация: Yjs (CRDT)

Yjs — наиболее зрелая CRDT-библиотека для real-time редакторов. Из коробки: компактные бинарные
апдейты, протокол присутствия (awareness), `UndoManager` с отменой только своих действий, офлайн
через IndexedDB, готовые серверы синхронизации.

Отклонённые альтернативы:

- **Automerge** — есть официальная Java-обёртка, что удобно для JVM-сервера, но нет встроенного
  undo для отдельного участника и экосистема для real-time UI беднее.
- **Собственная модель с авторитетным сервером** (свойства по принципу last-writer-wins, как в Figma) —
  сервер полностью на Kotlin и полный контроль над моделью, но клиентский движок синхронизации
  (оптимистичные апдейты, rebase, undo в мультиплеере) придётся писать с нуля. Слишком дорого для MVP.

### Collab-сервер: Hocuspocus

Серверу синхронизации нужно понимать Yjs-документ: отвечать на sync step 1 вычислением диффа,
сливать апдейты, сохранять компактный снапшот. Зрелой JVM-реализации Yjs нет, поэтому на Kotlin
это возможно только через нативную библиотеку.

Hocuspocus решает это готовыми хуками для аутентификации и хранения, масштабированием через Redis
и вебхуками. Код на Node.js минимален, бизнес-логика остаётся в Kotlin.

Альтернатива — **всё на JVM**: WebSocket-сервер на Kotlin + `yrs` (Rust-порт Yjs) через
C-биндинги `yffi` и Foreign Function & Memory API (JDK 22+).

- Плюсы: один рантайм на бэкенде, сервер может читать содержимое документа (поиск, серверный экспорт).
- Минусы: нативная библиотека под каждую платформу; ошибка в нативном коде роняет JVM; протоколы
  sync и awareness придётся реализовать самим.

К этому варианту можно перейти позже: Yjs-документ и формат хранения не меняются, на клиенте
меняется только провайдер.

### Холст: maxGraph

Решающее требование — полноценный импорт и экспорт `.drawio`. Файл `.drawio` — это сериализованная
модель mxGraph: ячейки со строками стилей draw.io (`rounded=1;fillColor=#dae8fc;edgeStyle=orthogonalEdgeStyle`).
Чтобы импортированная диаграмма выглядела так же, как в draw.io, нужна вся эта система стилей:
фигуры, периметры, маршрутизация рёбер, стрелки, позиционирование подписей, контейнеры.

- maxGraph — TypeScript-наследник mxGraph, движка draw.io (Apache-2.0). Модель и стили у него те же,
  что в `.drawio`, поэтому диаграммы отображаются так же, как в draw.io.
- Из коробки: ортогональная маршрутизация рёбер с точками изгиба, точки подключения, группы,
  контейнеры, swimlane-дорожки, редактирование подписей на холсте, зум/пан, отрисовка в SVG.
- Сотни элементов — комфортный объём для SVG-отрисовки.

Риски:

- Версия ещё до 1.0, API может меняться. Фиксируем версию и закрываем движок своей обёрткой.
- API императивный. React отвечает за интерфейс вокруг холста (панели, тулбар, библиотека фигур),
  холст живёт в отдельном компоненте.
- Связку Yjs ↔ модель maxGraph пишем сами: локальные изменения модели превращаются в транзакцию
  Yjs, а удалённые изменения применяются к модели с пометкой origin, чтобы не зациклиться.
  Это основной нетривиальный код на фронтенде.

Риски ограничены тем, что источник истины — наш Yjs-документ, а не модель maxGraph: рендерер можно
заменить, не трогая синхронизацию и хранение.

Отклонённые альтернативы:

- **React Flow** — проще связывается с Yjs и удобнее для React, но систему стилей draw.io
  (фигуры, маршрутизацию, стрелки, подписи) пришлось бы реализовать самим, иначе импорт теряет
  оформление.
- **Форк draw.io** (Apache-2.0) — полная совместимость, но огромная кодовая база на старом JS,
  рассчитанная на однопользовательскую работу.
- **Konva / PixiJS** (Canvas/WebGL) — максимальная производительность, но выделение, hit-testing,
  коннекторы и редактирование текста придётся писать самим.
- **tldraw SDK** — сильный движок с мультиплеером, но для продакшена нужен лицензионный ключ.
- **Excalidraw** — MIT, но стиль «от руки» и собственная модель данных не подходят для draw.io-подобных
  диаграмм.

### Импорт и экспорт `.drawio`

- Выполняются на клиенте: файл → модель maxGraph → Yjs-документ новой доски, и обратно.
- Содержимое `<diagram>` бывает обычным XML или сжатым (deflate + base64). Импорт поддерживает
  оба варианта, экспорт пишет несжатый XML.
- Каждая страница файла становится страницей доски.
- Фигуры из библиотек draw.io (AWS, UML, BPMN и т. п.) описаны XML-стенсилами. Подключаем их
  по мере надобности, а до тех пор такие фигуры показываются упрощённо, но их стиль не теряется
  и уходит обратно при экспорте.

### Backend: Kotlin + Spring Boot

- Экспертиза команды.
- Экосистема: Spring Security (OAuth2 Client, выпуск JWT), Flyway, Actuator + Micrometer,
  интеграция с Testcontainers, springdoc-openapi.
- **Ktor** — легче и изначально построен на корутинах, но ради экосистемы выбран Spring Boot.
- **Node.js (TypeScript)** — убрал бы отдельный `collab` (Yjs работает на сервере нативно) и дал бы
  общие типы с фронтендом, но ценой экспертизы команды и строгости типов во время выполнения.
- **Go** — лёгкий рантайм и маленькие образы, но зрелой реализации Yjs нет и там, так что `collab`
  на Node всё равно понадобится. По сравнению с Kotlin выигрыша нет, а доменную модель описывать
  менее выразительно.
- **Kotlin на фронтенде** (Kotlin/JS, Compose for Web) не рассматривается: для Yjs и движков
  диаграмм пришлось бы писать обёртки.

## Последствия

**Плюсы**

- Проверенная синхронизация из коробки — MVP быстрее.
- Совместимость с `.drawio` без потерь: та же модель и тот же движок отрисовки.
- Бизнес-логика и схема БД — в Kotlin.
- Рендерер и collab-сервер можно заменить независимо друг от друга.

**Минусы**

- Два серверных рантайма (JVM и Node.js): два Docker-образа и два пайплайна в CI.
- Связку Yjs ↔ maxGraph пишем сами, и maxGraph ещё не достиг 1.0.
- Серверная обработка содержимого диаграмм (поиск по тексту, серверный экспорт) потребует Node.js
  или `yrs`.

## Решённые вопросы

- Backend — Kotlin + Spring Boot (Ktor, Node.js и Go рассмотрены выше).
- Collab-сервер — Hocuspocus; переход на `yrs` возможен позже.
- Размер диаграмм — сотни элементов.
- `.drawio` — импорт и экспорт. Из-за этого холст — maxGraph, а не React Flow.
