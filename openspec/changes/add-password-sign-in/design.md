## Context

Вход построен на `oauth2Login` Spring Security: GitHub, Google и провайдеры OIDC (`CodrawClientRegistrations`).
Гость и тестовый вход e2e обходятся без провайдера: контроллер создаёт пользователя и кладёт в сеанс
`OAuth2AuthenticationToken` с `DefaultOAuth2User`, названным id пользователя (`signInToSession` в `SessionSignIn.kt`).
Весь остальной код читает id пользователя из `OAuth2User` и о способе входа не знает. Учётная запись — строка
`users(provider, provider_user_id, name, avatar_url, …)` с уникальной парой `(provider, provider_user_id)`;
`UserService.signIn(profile, previousUserId)` делает upsert и переносит гостя. Сеансы хранит Spring Session JDBC
с id пользователя в `spring_session.principal_name`; `Accounts.endSessions` удаляет их при блокировке и удалении
учётной записи. Пределы по адресу считает `AddressRateLimiter` в памяти процесса.

## Goals / Non-Goals

**Goals:**

- Постоянная учётная запись без внешних сервисов: логин и пароль, регистрация самим пользователем.
- Безопасность по умолчанию: вход по паролю выключен, пока оператор его не включит; хеш медленный и с солью;
  перебор и перечисление логинов затруднены; смена пароля завершает чужие сеансы.
- Всё, что работает для пользователей GitHub, работает и для пользователей с паролем: перенос гостя, блокировка,
  администраторы, удаление учётной записи и выгрузка данных.

**Non-Goals:**

- Почта у учётной записи, подтверждение почты и сброс пароля по почте: пользователь просил «просто логин и пароль».
  Забытый пароль сейчас не восстановить; администратор может удалить учётную запись. Сброс администратором — отдельное
  изменение.
- Создание учётных записей администратором, приглашения, двухфакторная аутентификация, passkeys.
- Привязка пароля к учётной записи GitHub, Google или корпоративной и наоборот.
- Проверка пароля по базам утёкших паролей: это внешний сервис или большой словарь в образе.
- Смена логина.

## Decisions

### Учётная запись: `provider = 'password'`, `provider_user_id` = логин в нижнем регистре

Пользователь с паролем — обычная строка `users` с `provider = 'password'` и `provider_user_id = lower(login)`; имя —
логин так, как его ввели при регистрации. Уникальность логина без учёта регистра даёт уже существующее ограничение
`(provider, provider_user_id)`, поэтому новый столбец и новый индекс в `users` не нужны, а админка, поиск
пользователей и выгрузка данных работают без изменений. Альтернатива — столбец `login` в `users` — отклонена: он пуст у
всех остальных пользователей и требует своего ограничения уникальности.

### Хеш пароля в отдельной таблице

```sql
CREATE TABLE password_credentials (
    user_id       uuid PRIMARY KEY REFERENCES users (id) ON DELETE CASCADE,
    password_hash text NOT NULL,
    changed_at    timestamptz NOT NULL
);
```

Отдельная таблица держит хеш вне `SELECT * FROM users`, которым читают пользователя повсюду, и вне выгрузки данных
(`AccountExportService` читает `users`). `ON DELETE CASCADE` удаляет хеш вместе с учётной записью — удаление учётной
записи администратором и самим пользователем ничего нового не делает. Миграция `V33` и откат `U33`.

### bcrypt через `DelegatingPasswordEncoder`

`PasswordEncoderFactories.createDelegatingPasswordEncoder()` из `spring-security-crypto` (уже в зависимостях) пишет
хеш как `{bcrypt}$2a$10$…`: соль внутри, стоимость 10 (≈ 70 мс). Префикс алгоритма позволяет потом сменить
алгоритм или стоимость: при успешном входе `upgradeEncoding` говорит, устарел ли хеш, и тогда он пересчитывается.
Argon2id лучше по памяти, но в Spring Security ему нужна BouncyCastle — новая большая зависимость ради одной функции;
PBKDF2 без памяти слабее bcrypt против GPU. bcrypt принимает не больше 72 байт пароля (Spring Security отказывает
длиннее), поэтому это верхний предел пароля, и регистрация сообщает о нём сама. ADR-0015 фиксирует выбор.

### Правила логина и пароля

- Логин: 3–32 символа `[A-Za-z0-9._-]`, первый — буква или цифра. Только латиница: кириллица и латиница рядом дают
  неотличимые на глаз логины (`а` и `a`). Сравнение без учёта регистра.
- Пароль: не меньше 8 символов (NIST SP 800-63B), не больше 72 байт UTF-8, не равен логину без учёта регистра.
  Никаких требований к классам символов: они не помогают и мешают длинным фразам.

Проверяет `backend`; фронтенд повторяет правила только для подсказок у полей. Ответ на нарушение — 400 с
`reason`: `login-invalid`, `password-short`, `password-long`, `password-login`.

### API

`PasswordController` в новом пакете `password` (там же `PasswordService`, `PasswordCredentials`, `PasswordLimiter`, правила):

- `POST /api/auth/password/sign-up` `{login, password}` — открыт без входа. 204 и сеанс; 409 `login-taken`;
  403 `login-reserved` для логина из `CODRAW_ADMINS`; 400 с причиной из правил; 403, если вход по паролю или
  регистрация выключены; 429 с `Retry-After` сверх предела регистраций с адреса.
- `POST /api/auth/password/sign-in` `{login, password}` — открыт без входа. 204 и сеанс; 401 `invalid-credentials`
  для неизвестного логина и неверного пароля одинаково; 403 `blocked` для заблокированного (только после верного
  пароля, чтобы блокировка не выдавала существование логина); 403, если вход по паролю выключен; 429 с
  `Retry-After` сверх предела неудачных попыток.
- `PUT /api/me/password` `{currentPassword, newPassword}` — с сеансом. 204; 400 `wrong-password`, если текущий
  неверен (считается неудачной попыткой по логину); 400 с причиной из правил для нового; 403, если у пользователя нет
  пароля.

Оба открытых эндпоинта идут под CSRF, как `POST /api/guest`: фронтенд берёт токен из cookie `XSRF-TOKEN`. Сеанс
создаёт тот же `signInToSession` с `provider = 'password'` (новый id сеанса против фиксации сеанса), а срок сеанса —
обычный `server.servlet.session.timeout`, как после входа через провайдера, даже если до этого был гостевой сеанс на
30 дней. Своя форма вместо `formLogin` Spring Security: тот отдаёт редиректы и `application/x-www-form-urlencoded`, а
весь остальной вход и `principal` устроены на `OAuth2User`.

### Неотличимость неверного логина и неверного пароля

Неизвестный логин всё равно проверяется против постоянного хеша-пустышки, вычисленного при старте тем же
кодировщиком, поэтому время ответа то же, что и для неверного пароля. Ответ — один и тот же 401. Регистрация, конечно,
сообщает, что логин занят: без почты иначе нельзя; её предел по адресу ограничивает перебор логинов через неё.

### Пределы

Новые настройки `codraw.limits`:

- `password-failures-per-address-per-hour` (30) — неудачные попытки входа и смены пароля с одной сети
  (`AddressRateLimiter.networkOf`: IPv4-адрес, IPv6 /64);
- `password-failures-per-login-per-hour` (10) — неудачные попытки по одному логину с любых адресов;
- `sign-ups-per-address-per-hour` (10) — регистрации с одной сети.

Удачные входы не считаются: офис за одним NAT утром входит весь сразу. Поэтому лимитер умеет и проверить окно, не
расходуя его (`AddressRateLimiter.waitFor`), и расходовать: перед проверкой пароля — `waitFor` по адресу и логину,
после неудачи — `acquire` по обоим. Предел по логину позволяет злоумышленнику на час не пускать конкретного
пользователя; это обычная цена защиты от перебора, и окно короткое. Счётчики в памяти, как у гостей: при нескольких
экземплярах `backend` предел умножается на их число. Каждый отказ по пределу — `codraw_limits_reached_total` с
тегами `password-failures` и `sign-ups`.

### Перенос гостя и блокировка

`UserService` получает `signUp(profile, previousUserId): User?` — `INSERT … ON CONFLICT DO NOTHING RETURNING *`,
`null` для занятого логина — и `signInExisting(user, previousUserId)`. Обе переносят гостя тем же кодом, что и
`signIn(profile, previousUserId)` (вынесен в `transferGuest`). Вход по паролю не делает upsert: имя у такого
пользователя не меняется.

### Смена пароля завершает остальные сеансы

`PUT /api/me/password` в одной транзакции пишет новый хеш и удаляет из `spring_session` все сеансы пользователя,
кроме текущего: тот, кто узнал старый пароль и вошёл с ним, выходит, а collab закрывает его соединения при следующей
проверке, как после блокировки.

### Администраторы

`AdminProperties` принимает `password:<логин>`; логин приводится к нижнему регистру. Логин зарегистрировать может кто
угодно, поэтому, если оператор впишет `password:admin` раньше, чем сам зарегистрируется, `admin` мог бы занять
посторонний и стать администратором. Регистрация логина из `CODRAW_ADMINS` поэтому отвечает 403 `login-reserved`;
`docs/deploy.md` говорит: сначала зарегистрируйтесь, потом впишите логин в `CODRAW_ADMINS` и перезапустите `backend`.

### Способы входа и страница входа

`GET /api/auth/providers` получает `password: {signUp: boolean} | null` — `null`, если вход по паролю выключен.
Страница входа: при включённом входе по паролю сверху форма «Логин», «Пароль», «Войти» и ссылка
«Зарегистрироваться», которая переключает форму на «Логин», «Пароль», «Повторите пароль», «Зарегистрироваться» и
«Уже есть учётная запись? Войти»; ниже, после «или», — кнопки провайдеров и «Продолжить без входа». «Вход не
настроен» — когда нет ни провайдеров, ни пароля, ни гостей. Страница приглашения в пространство, где гостю показаны
кнопки провайдеров, при входе по паролю показывает ссылку «Войти по логину и паролю» на страницу входа с возвратом
обратно.

`/api/me` получает `password: boolean` — вошёл ли пользователь по паролю; страница «Учётная запись» показывает ему
раздел «Пароль» с формой смены.

### Политика конфиденциальности

`/api/legal` получает `passwords: boolean`. Когда вход по паролю включён, «Учётная запись» говорит: логин, который
пользователь выбрал, и хеш пароля; сам пароль не хранится и никуда не передаётся; логин виден участникам досок как
имя. «Технические данные» — что сетевой адрес и логин на короткое время в памяти сервера ограничивают неудачные
попытки входа и регистрации. Удаление учётной записи — что хеш удаляется, а логин освобождается.

## Risks / Trade-offs

- [Нет сброса пароля] → забывший пароль теряет учётную запись; администратор может её удалить, а доски с участниками
  остаются им. Сброс администратором и почта — следующие изменения; README и справка об этом говорят.
- [Самостоятельная регистрация открывает установку] → по умолчанию вход по паролю выключен, регистрацию можно
  выключить отдельно, а регистрации с адреса ограничены. Гостевой вход, включённый по умолчанию, открывает установку
  не меньше.
- [Предел по логину позволяет не пускать чужой логин] → окно — час; удачный вход с верным паролем всё равно не
  пройдёт, пока окно не кончится. Компромисс сознательный.
- [Счётчики в памяти] → перезапуск `backend` их сбрасывает; при нескольких экземплярах пределы умножаются. Так же
  устроены пределы гостей и отзывов.
- [72 байта bcrypt] → пароль из 36 кириллических букв — уже предел; форма говорит об этом сообщением, а не обрезает
  пароль молча.

## Migration Plan

Миграция `V33` добавляет `password_credentials`; откат `U33` удаляет таблицу, а с ней и пароли: учётные записи
`password` остаются, но войти в них нельзя, пока вход по паролю не вернут. Установки без
`CODRAW_PASSWORDS_ENABLED=true` после обновления ведут себя как раньше.
