# Design

## Context

Фронтенд, API и синхронизация работают на одном origin: в разработке через прокси Vite, в продакшене
через nginx. В ADR-0001 решено обойтись в MVP без отдельного IdP: вход через GitHub и Google,
`collab` проверяет JWT, выпущенный `backend`. Требования — в `specs/`.

## Goals / Non-Goals

**Goals:**

- Ни один токен не хранится в JavaScript-доступном хранилище браузера.
- `collab` проверяет доступ без запроса в `backend` на каждое подключение.

**Non-Goals:**

- Совместный доступ, приглашения и роли — следующее изменение.
- Вход по паролю, Keycloak и корпоративный SSO.
- Очистка заброшенных гостевых учётных записей и их досок.

## Decisions

### REST: сессия в cookie

- Spring Security OAuth2 Client с провайдерами GitHub и Google.
- После входа — сессия в HttpOnly cookie с `SameSite=Lax`, хранится в PostgreSQL через Spring Session
  JDBC, поэтому `backend` можно запускать в нескольких экземплярах.
- CSRF — cookie `XSRF-TOKEN` и заголовок `X-XSRF-TOKEN`, который фронтенд добавляет к изменяющим
  запросам.
- Для `/api/**` неаутентифицированный запрос получает 401, а не редирект: SPA сама показывает
  страницу входа.

Альтернатива — JWT для REST в `localStorage`. Отклонена: токен доступен любому XSS.

### Синхронизация: токен на конкретную доску

- `POST /api/boards/{id}/collab-token` возвращает JWT со сроком жизни 5 минут.
- Claims токена: `sub` (id пользователя), `board` (id доски), `name`, `avatar`, `aud = codraw-collab`.
- Подпись — асимметричный ключ `backend`. Публичная часть доступна по `/.well-known/jwks.json`.
  В продакшене ключ передаётся через переменную окружения, в разработке генерируется при старте.
- `collab` в `onAuthenticate` проверяет подпись по кэшированному JWKS, `aud`, срок и совпадение
  `board` с именем документа.
- Провайдер на фронтенде получает токен асинхронной функцией перед каждым подключением, поэтому
  переподключение после истечения срока работает само.

Альтернатива — `collab` спрашивает у `backend` права на каждое подключение. Отклонена: лишний сетевой
вызов и зависимость от доступности `backend` в момент подключения. Цена — отозванный доступ действует
до закрытия соединения. Пока у доски один владелец, это неважно.

### Данные

```
users  (id uuid PK, provider text, provider_user_id text, name text, avatar_url text, created_at,
        UNIQUE (provider, provider_user_id))
boards.owner_id uuid NOT NULL → users
```

Повторный вход через того же провайдера находит пользователя по `(provider, provider_user_id)`
и обновляет имя и аватар.

### Гости

- `POST /api/guest` доступен без сеанса и требует CSRF-токен. Он создаёт пользователя с
  `provider = guest`, случайным `provider_user_id` и именем «Гость N» (N — случайное от 1 до 999) без
  аватара и открывает для него сеанс. Если сеанс уже есть, эндпоинт оставляет его: повторное «Продолжить
  без входа» не создаёт нового гостя.
- Гость — обычный пользователь: владение досками, токены `collab` и проверки доступа для него те же.
- Сеанс гостя живёт 30 дней без обращений (`maxInactiveInterval`), а cookie сеанса делается постоянной через
  атрибут remember-me Spring Session, поэтому переживает закрытие браузера. Сеансы вошедших через
  провайдера не меняются.
- При входе через провайдера из гостевого сеанса доски гостя передаются вошедшему пользователю
  (`UPDATE boards SET owner_id`) в том же запросе, где создаётся или обновляется пользователь.
- `GET /api/me` возвращает признак `guest`; у гостя в шапке вместо «Выйти» кнопка «Войти»: выход отрезал бы
  его от досок.
- Cookie `XSRF-TOKEN` выставляется в ответ на любой запрос к API. Если её ещё нет (страница входа открыта
  напрямую или после выхода), фронтенд перед изменяющим запросом делает GET к API.

### Тестовый вход

Сквозные тесты не могут ходить в GitHub. В профиле `e2e` `backend` включает эндпоинт тестового
входа, которого нет в остальных профилях.

## Risks / Trade-offs

- [Тестовый вход случайно включится в продакшене] → бин создаётся только в профиле `e2e`, плюс тест,
  что в профиле по умолчанию эндпоинта нет.
- [Ротация ключа подписи разорвёт активные подключения] → JWKS публикует текущий и предыдущий ключи;
  `collab` перечитывает JWKS при неизвестном `kid`.
- [Отозванный доступ действует до переподключения] → токен живёт 5 минут; для мгновенного отзыва
  позже можно добавить сигнал от `backend` в `collab`.
- [Заброшенные гостевые учётные записи и их доски копятся в БД] → их очистка — отдельное изменение.
- [Гость, очистивший cookie, теряет доступ к своим доскам] → чтобы сохранить доски, гость входит через
  провайдера, и доски переходят к нему.

## Migration Plan

1. Пара миграций V/U: создать `users` и таблицы Spring Session, удалить доски без владельца, добавить
   `boards.owner_id NOT NULL`.
2. Выкатить `backend`, затем `collab` с проверкой токена, затем `frontend`.
3. Откат — миграция U и предыдущие версии сервисов.
