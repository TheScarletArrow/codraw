# Design

## Context

Импорты инфраструктуры (`infra/`) строят `InfraGraph` — узлы с фигурой и строками подписи, рамки, связи — и
`infraCells` раскладывает его слева направо и ставит на страницу. Сборка Gradle — не инфраструктура, но её схема
устроена так же: модули — узлы, группы модулей — рамки, зависимости — связи. Достоверно состав сборки знает только сам
Gradle: модули могут подключаться циклом по папкам, плагины — через convention-плагины `buildSrc`, зависимости — через
общие блоки в корне.

## Goals / Non-Goals

**Goals:**

- Точная схема модулей без ручной работы — из графа, который печатает Gradle.
- Схема без запуска Gradle — из файлов сборки, с честной сводкой того, что не разобрано.

**Non-Goals:**

- Внешние библиотеки, Maven, включённые сборки, полное понимание Kotlin DSL и Groovy.

## Decisions

### Скрипт инициализации, а не плагин и не задача в сборке

`codraw.gradle` подключается флагом `-I` и ничего не пишет в проект: ни плагина в `settings.gradle`, ни задачи в
`build.gradle`. В `gradle.projectsEvaluated` он обходит `rootProject.allprojects`: путь, имя, известные плагины
(`pluginManager.hasPlugin` по списку идентификаторов — сами объекты плагинов не знают своих id) и объявленные в
конфигурациях `ProjectDependency` с именем конфигурации. JSON строится при конфигурации и только печатается задачей
`codrawGraph`, поэтому скрипт работает и с configuration cache, в том числе при повторном использовании кэша (проверено на
Gradle 9.8). Скрипт на Groovy, а не на Kotlin DSL: `ProjectDependency.path` появился в Gradle 8.11, а
`dependencyProject` убран в Gradle 9 — Groovy обращается к тому, что есть (`hasProperty('path')`), без ошибки
компиляции скрипта ни в одной из версий. Скрипт лежит в `infra/codraw.gradle` и попадает в сборку фронтенда как
текст (`?raw`), «Скачать codraw.gradle» сохраняет его через `downloadBlob` — без отдельного адреса на сервере и без
связи с сервером.

### Разбор файлов сборки — без Gradle и с границами

Чтение папки — `<input webkitdirectory>`: из списка файлов берутся только файлы сборки вне служебных папок, их текст
читается, остальное не открывается. Комментарии вырезаются, строки остаются. `include` разбирается до закрывающей
скобки (Kotlin DSL) или до конца строки с продолжением после запятой (Groovy); `include` с аргументами не из строк
(цикл по папкам) пропускается и считается. Зависимости ищутся только внутри блоков `dependencies { … }` (подсчёт
скобок) — так `tasks.dependsOn(project(":x").tasks…)` не становится зависимостью. Typesafe accessors `projects.a.bB`
сопоставляются с путями без учёта регистра, `-` и `_`, как их строит Gradle. Плагины — из `plugins { … }` и
`apply plugin:`; у `alias(libs.plugins.spring.boot)` идентификатор неизвестен без каталога версий, поэтому
технология узнаётся по словам имени (`spring.boot`, `kotlin.jvm`, `android.application`). Convention-плагины
(`id("shop.kotlin-conventions")`) технологий не дают — об этом подсказка окна: точнее всего граф из скрипта.

### Модель сборки и граф

И скрипт, и файлы дают одну модель: проекты с путём, именем, плагинами и зависимостями, и число пропущенного. Граф:

- группа — проект без плагинов и зависимостей (исходящих и входящих), внутри которого есть другие проекты (в скрипте
  это неявные родители `:services`, в файлах — путь-префикс); у узла рамка — ближайшая группа-родитель; рамки плоские;
- корень без плагинов и зависимостей не рисуется: рамка вокруг всего ничего не говорит;
- технологии — по таблице плагинов: язык (Kotlin JVM, Kotlin Multiplatform, иначе Java, потому что Kotlin JVM
  применяет и `java`), затем фреймворки;
- тестовые конфигурации (`/test/i`: `testImplementation`, `androidTestImplementation`, `testFixturesApi`) — под
  галочкой; конфигурации `…Classpath`, `…Elements` и `…DependenciesMetadata` не объявляют зависимостей и не
  рассматриваются.

### Раскладка сверху вниз

Модули читают от приложения вниз к ядру — привычно для схем слоёв. `InfraGraph` получает необязательное направление,
`infraCells` передаёт его `layoutShapes` (у compose и Kubernetes по-прежнему слева направо). Место под подписи связей
раскладка оставляет по высоте, а подписи конфигураций короткие.

### Окно

Своё окно `GradleImport.tsx`, а не формат `InfraImport`: у Gradle другой ввод (папка и граф вместо файлов YAML),
другие галочки и кнопка скрипта. Общие с ним — сводка, ошибки, `infraCells`, добавление через меню.

## Risks / Trade-offs

- [Разбор файлов ошибается на нетиповой сборке] → сводка называет пропущенные `include`, подсказка ведёт к скрипту;
  результат правится на доске как обычная схема.
- [Chrome спрашивает «загрузить N файлов на сайт?» при выборе папки] → окно говорит, что файлы читаются в браузере и
  никуда не отправляются; граф из скрипта — один файл без этого вопроса.
- [Скрипт сломается на будущей версии Gradle] → он использует только устойчивый API (`allprojects`, `configurations`,
  `pluginManager`, `ProjectDependency`), а путь берёт из того свойства, которое есть.
