# Design

## Context

Таблица базы данных на доске — элемент-фигура `table` со строками-потомками: поля (`имя тип PK FK NOT NULL UNIQUE`) и
строки индексов (`имя (столбцы) UNIQUE USING метод …`, ключ стиля `codrawIndex`). Внешний ключ — связь между полями;
какой её конец ссылается, решает `sourceRefers`. Базовая таблица (`codrawBase`) — шаблон полей: таблицы-наследники
держат копии её полей своими элементами (id `<таблица>:<поле базы>`, ключ `codrawInherited`), и выгрузка SQL
(`diagramSchema`, `schemaSql`) пропускает базовые таблицы и связи с их полями. СУБД таблицы — ключ стиля `dbVendor`.

Сравнение двух состояний доски (`diagram/diff.ts`) читает документы в простые снимки (`BoardSnapshot`: страницы по id,
элементы по id) — и версию в просмотре версии, и живую доску. Просмотр предложения сравнивает основу и черновик, а
принятие сливает разницу с доской (`mergeProposal`). Окна приложения — поповеры shadcn/ui (`Popover`), выгрузка файлов —
`downloadBlob`, буфер обмена — `navigator.clipboard.writeText`, как в «SQL и Mermaid». Требования — в `specs/`.

## Goals / Non-Goals

**Goals:**

- Миграция из разницы двух состояний доски, которую можно запустить: правильный порядок операторов, переименования
  вместо удаления и добавления, имена ограничений, которые следующая миграция найдёт.
- Синтаксис PostgreSQL, MySQL / MariaDB, Oracle и SQL Server; SQLite и ClickHouse — в пределах их `ALTER TABLE`.
- SQL, пара Flyway `V`/`U` и changeset Liquibase с откатом — одним генератором.
- Генератор — чистые модули с исчерпывающими unit-тестами; интерфейс тонкий.

**Non-Goals:**

- Перевод типов между СУБД: типы пишутся, как на доске (`uuid` останется `uuid` и в Oracle). СУБД по умолчанию — СУБД
  таблиц, поэтому типы обычно совпадают с её синтаксисом.
- `DEFAULT`, `CHECK`, `COLLATE`, `AUTO_INCREMENT`, составные внешние ключи, представления, функции, данные: их нет и в
  выгрузке SQL (`schemaSql`), а значит, и в модели схемы.
- Сравнение с базой данных: генератор не знает реальной схемы базы и считает, что она совпадает с исходным состоянием
  доски, а ограничения названы так, как их назвал бы PostgreSQL (как и при выгрузке `schemaSql`).
- Миграция между двумя версиями или с прошлого визита — кнопка есть только там, где сравнение «было → станет» имеет
  смысл для миграции: версия → доска и доска → предложение.

## Decisions

### Схема состояния с идентификаторами

- `diagramSchema` перестраивается поверх нового `diagramTables(cells)`: таблицы страницы с id ячеек — таблицы, полей,
  строк индексов и связей внешних ключей (и id полей на обоих концах связи), а также стилем таблицы (для `dbVendor`) и
  типом поля, как он написан (`splitField`): `SqlColumn.type` хранит тип в нижнем регистре для сравнения, а ClickHouse
  различает регистр типов (`String`, `UInt64`). Правила те же, что у выгрузки: базовые таблицы пропускаются вместе со
  связями к их полям, унаследованные копии полей — столбцы наследников, поле без имени пропускается. `diagramSchema`
  остаётся проекцией без id, и выгрузка SQL, Mermaid и буфер обмена не меняются.
- `boardSchema(snapshot)` (`sql/migration.ts`) обходит страницы снимка по порядку, а элементы страницы — в порядке
  дерева (`treeOrder`), и даёт таблицам, полям и индексам ключи `<страница>/<элемент>`: id ячеек уникальны только в
  пределах страницы. Внешний ключ — пара «поле → поле, на которое оно ссылается» по их ключам; две связи между теми же
  полями — один ключ.
- Одно имя дважды в одном состоянии (таблица на двух страницах, например после «Дублировать страницу»; два поля или два
  индекса с одним именем в таблице) — в базе такого не бывает: берётся первое по порядку страниц и элементов, а SQL
  начинается с комментария, какие таблицы нарисованы несколько раз.

### Сопоставление двух состояний

- Таблицы, поля внутри сопоставленных таблиц и индексы внутри них сопоставляются сначала по ключу, затем оставшиеся без
  пары — по имени. Тот же ключ с другим именем — переименование, никогда удаление и добавление. Совпадение по имени
  нужно для элементов, которые пришли новыми ячейками с прежним смыслом: таблица на дубликате страницы, удалённой
  оригинальной; таблица, заново импортированная из SQL. Альтернатива — только по ключу — отклонена: удаление одной из
  двух копий таблицы дало бы `DROP TABLE` с данными.
- Внешние ключи сопоставляются по смыслу — по сопоставленным полям обоих концов, а не по id связи: перерисованная
  связь между теми же полями — не изменение.
- Типы сравниваются без учёта регистра и пробелов и с синонимами (`int`/`int4`/`integer`, `bool`/`boolean`,
  `timestamptz`/`timestamp with time zone`, `varchar`/`character varying`, `decimal`/`numeric`, `float8`/`double
  precision`, …): смена записи типа без смены типа — не изменение (`sql/sqlTypes.ts`).

### Имена ограничений

- У ключей на доске нет имён, поэтому генератор даёт имена, которые PostgreSQL даёт ограничениям без имени:
  `<таблица>_pkey`, `<таблица>_<столбец>_key`, `<таблица>_<столбец>_fkey` — с тем же усечением длинных имён (алгоритм
  `makeObjectName`: укорачивается более длинная из частей, пока имя не войдёт в предел байтов). Так база, созданная из
  «Скачать .sql» или PostgreSQL без явных имён, совпадает с именами миграции. Предел — 63 байта PostgreSQL, 64 MySQL,
  128 Oracle и SQL Server; SQLite и ClickHouse не ограничивают.
- `CREATE TABLE` и `ADD CONSTRAINT` всегда называют ограничения явно — иначе SQL Server и Oracle дали бы случайные имена,
  и следующая миграция не смогла бы их снять.
- Переименование таблицы или столбца меняет производные имена его ограничений. Чтобы имена в базе оставались
  производными от текущих (и следующая миграция их нашла), миграция переименовывает ограничения вслед за ними:
  PostgreSQL и Oracle — `RENAME CONSTRAINT`, SQL Server — `sp_rename … 'OBJECT'`, уникальный ключ MySQL —
  `RENAME INDEX`. Где переименовать нельзя (внешний ключ MySQL, уникальный индекс SQLite), ограничение снимается под
  старым именем и добавляется под новым; где имени нет или оно не используется (первичный ключ MySQL — всегда `PRIMARY`,
  первичный и внешние ключи SQLite, ClickHouse) — ничего.

### План: изменения и порядок операторов

- План — список операций без синтаксиса (`dropForeignKey`, `dropIndex`, …, `addForeignKey`), сгруппированных по фазам;
  диалект превращает каждую операцию в оператор или в комментарий «не умеет». Фазы:
  1. снять внешние ключи — удалённые, изменённые и те, что зависят от снимаемых ключей;
  2. снять индексы, ограничения `UNIQUE` и первичные ключи — удалённые и изменённые;
  3. удалить столбцы, удалить таблицы, переименовать таблицы, столбцы, индексы и ограничения;
  4. создать таблицы (столбцы, первичный ключ, `UNIQUE`);
  5. добавить столбцы;
  6. изменить столбцы — тип и `NOT NULL`;
  7. добавить первичные ключи и `UNIQUE`, создать индексы;
  8. добавить внешние ключи.
  Удаление до переименования освобождает имя (`DROP COLUMN b`, затем `RENAME COLUMN a TO b`); переименование до
  создания — тоже. Внешние ключи в конце не зависят от порядка создания таблиц. Фазы 1–3 пишут прежние имена таблиц и
  ограничений, фазы с 3-й (после переименований) — новые.
- Переименования упорядочиваются: переименование ждёт, пока его новое имя освободит другое переименование
  (`b → c` раньше `a → b`); цикл (`a ↔ b`) разрывается временным именем `<имя>_tmp` (с числом, если занято). Таблицы,
  индексы и ограничения — в одном пространстве имён схемы (в PostgreSQL индексы и ограничения-индексы делят его с
  таблицами), столбцы — в пределах таблицы.
- Индекс изменён, если после замены переименованных столбцов в его тексте (`mapIndexColumns` из `sql/tableIndex.ts`)
  отличаются столбцы, `UNIQUE`, метод или остальное (`WHERE …`): тогда он снимается и создаётся заново; изменилось только
  имя — переименование. Первичный ключ изменён, если изменился набор его столбцов; `UNIQUE` столбца — если пометка
  появилась или пропала (`UNIQUE` у единственного столбца первичного ключа не пишется, как и в выгрузке).
- Внешний ключ пересоздаётся, если сменился тип столбца на любом его конце (MySQL и SQL Server иначе не меняют тип),
  и если снимается первичный ключ, `UNIQUE` или уникальный индекс, на который он опирается (PostgreSQL не снимет
  ограничение, от которого зависит внешний ключ). Внешние ключи между двумя удаляемыми таблицами снимаются явно, чтобы
  `DROP TABLE` не зависел от порядка; свои внешние ключи удаляемой таблицы и её индексы уходят вместе с ней.
- SQL Server не меняет тип столбца, который входит в индекс или ограничение: для него такие индексы, первичный ключ и
  `UNIQUE` снимаются и создаются заново (признак диалекта `rebuildsKeysOnRetype`).
- Обратная миграция — тот же план из нового состояния в старое: переименования и производные имена в ней сходятся
  с прямой.

### Диалекты

| | PostgreSQL | MySQL / MariaDB | Oracle | SQL Server | SQLite | ClickHouse |
|---|---|---|---|---|---|---|
| Кавычки имени | `"…"` | `` `…` `` | `"…"` | `[…]` | `"…"` | `` `…` `` |
| Таблица | `ALTER TABLE a RENAME TO b` | так же | так же | `EXEC sp_rename N'a', N'b'` | так же | `RENAME TABLE a TO b` |
| Столбец | `RENAME COLUMN a TO b` | так же (MySQL 8.0, MariaDB 10.5.2) | так же | `sp_rename N't.a', N'b', N'COLUMN'` | так же (3.25) | так же |
| Новый столбец | `ADD COLUMN c тип [NOT NULL]` | так же | `ADD c тип [NOT NULL]` | `ADD c тип NULL \| NOT NULL` | `ADD COLUMN` | `ADD COLUMN c тип` |
| Тип, `NULL` | `ALTER COLUMN c TYPE тип USING c::тип`, `SET/DROP NOT NULL` | `MODIFY COLUMN c тип [NOT NULL]` | `MODIFY c [тип] [NOT NULL \| NULL]` | `ALTER COLUMN c тип NULL \| NOT NULL` | комментарий | `MODIFY COLUMN c тип`; `NULL` — комментарий |
| Первичный ключ | `ADD CONSTRAINT t_pkey PRIMARY KEY`, `DROP CONSTRAINT` | `ADD PRIMARY KEY`, `DROP PRIMARY KEY` | как PostgreSQL | как PostgreSQL | только в `CREATE TABLE` | `ORDER BY` в `CREATE TABLE` |
| `UNIQUE` | `ADD CONSTRAINT t_c_key UNIQUE` | `ADD UNIQUE KEY`, `DROP INDEX` | как PostgreSQL | как PostgreSQL | `CREATE UNIQUE INDEX` | комментарий |
| Внешний ключ | `ADD CONSTRAINT … FOREIGN KEY`, `DROP CONSTRAINT` | `DROP FOREIGN KEY` | как PostgreSQL | как PostgreSQL | только в `CREATE TABLE` | комментарий |
| Индекс | `CREATE INDEX n ON t USING m (…)`, `DROP INDEX n`, `ALTER INDEX … RENAME TO` | `USING BTREE\|HASH` после столбцов, `DROP INDEX n ON t`, `RENAME INDEX` | без метода, `ALTER INDEX … RENAME TO` | без метода, `DROP INDEX n ON t`, `sp_rename … 'INDEX'` | без метода, переименование — снять и создать | комментарий |

- Имя пишется без кавычек, если оно простое и не зарезервировано в этой СУБД; PostgreSQL — по `quoteName` выгрузки
  SQL. Для Oracle простое имя — в любом регистре и без кавычек: кавычки сделали бы имя чувствительным к регистру
  (`"users"` и `USERS` в Oracle — разные таблицы), а список зарезервированных слов — точный список Oracle. Для MySQL,
  SQL Server, SQLite и ClickHouse лишние кавычки безвредны, поэтому список слов, которые берутся в кавычки, — широкий
  общий. Имена столбцов в тексте индекса тоже переписываются кавычками этой СУБД, выражения остаются, как написаны.
- PostgreSQL меняет тип с `USING c::тип`: без него не приводятся, например, `text` → `integer`. SQL Server всегда пишет
  `NULL` или `NOT NULL` явно: без них `ALTER COLUMN` делает столбец обнуляемым. MySQL `MODIFY COLUMN` задаёт столбец
  заново — комментарий напоминает дописать `DEFAULT` и `AUTO_INCREMENT`, которых на доске нет.
- SQLite: `ALTER TABLE` умеет только переименования, `ADD COLUMN` и `DROP COLUMN` (3.35). Поэтому внешние ключи новой
  таблицы пишутся внутри её `CREATE TABLE` (SQLite не проверяет таблицу, на которую ссылается ключ, при создании),
  `UNIQUE` — уникальными индексами `<таблица>_<столбец>_key` (их можно снять), а смена типа и `NOT NULL`, первичного
  ключа и внешних ключей готовой таблицы — комментарий «таблицу нужно пересоздать».
- ClickHouse: `CREATE TABLE … ENGINE = MergeTree ORDER BY (первичный ключ)` (или `tuple()`), обнуляемость задаёт тип
  `Nullable(…)` — пометка `NOT NULL` не пишется; ограничений `UNIQUE`, внешних ключей и смены первичного ключа нет,
  индексы пропуска данных устроены иначе — для них комментарии.
- Комментарий вместо оператора — операция «не поддерживается»: сводка считает такие отдельно.
- Новый столбец `NOT NULL` без `DEFAULT` не добавится в таблицу со строками (PostgreSQL, Oracle, SQL Server), а в
  SQLite — вовсе: перед ним комментарий. MySQL и ClickHouse заполняют такие столбцы значениями по умолчанию типа.

### Опасные операции

- `DROP TABLE`, `DROP COLUMN` и смена типа, которая не известна как расширяющая, предваряются комментарием
  `-- ВНИМАНИЕ: …` и считаются в сводке «опасных». Расширяющие: тот же тип с большей длиной или точностью
  (`varchar(100)` → `varchar(255)`, `numeric(10,2)` → `numeric(12,2)`), длина снята (`varchar(n)` → `varchar`,
  `text`, `clob`, `nvarchar(max)`, `String`), целые и вещественные по возрастанию (`smallint` → `integer` → `bigint`,
  `real` → `double precision`, `Int32` → `Int64`), строковые типы MySQL (`text` → `mediumtext` → `longtext`), целое в
  `numeric` без точности. Остальное (в том числе `text` → `integer`) — опасно: значения могут не преобразоваться или
  обрезаться. Лучше предупредить лишний раз, чем промолчать.

### Форматы

- SQL: заголовок-комментарий (откуда и куда, СУБД, таблицы, нарисованные несколько раз), затем фазы через пустую строку;
  многострочный `CREATE TABLE` отделён пустыми строками.
- Flyway: `V<версия>__<описание>.sql` с прямой миграцией и `U<версия>__<описание>.sql` с обратной — как пары миграций
  `backend`. Версия — числа через `.` или `_` (`2`, `2.1`, `20261007_1`), иначе файлов нет и окно говорит, какой нужна
  версия. Описание: буквы и цифры (кириллица тоже — Flyway её принимает), остальное — `_`; пустое — `update_schema`.
- Liquibase — formatted SQL: `--liquibase formatted sql`, `--changeset автор:id`, `--comment:` откуда и куда, операторы
  прямой миграции и `--rollback` с каждой строкой обратной. Выбран вместо XML/YAML-changelog: он несёт тот же SQL
  выбранной СУБД, что Flyway и «SQL» (переименования `sp_rename`, условия частичных индексов, `USING`), а изменения XML
  (`renameColumn`, `addForeignKeyConstraint`, …) потребовали бы второго генератора с переводом в абстракции Liquibase,
  где теряются частичные индексы и методы, и отката для каждого вида изменения. Обратная миграция у нас уже есть — она
  и становится `--rollback`. Автор и ID без пробелов (пробелы становятся `_`, двоеточие из автора убирается): иначе
  Liquibase не разберёт строку `--changeset`.

### Окно «Миграция SQL»

- Поповер, как остальные окна приложения (`SqlMenu`, экспорт изображений): выбор «СУБД», переключатель «Формат» (SQL,
  Flyway, Liquibase), для Flyway — «Версия» и «Описание», для Liquibase — «Автор» и «ID changeset», сводка «Изменений:
  N · опасных: M · СУБД не умеет: K», предпросмотр каждого файла моноширинным полем только для чтения с его именем и
  «Скопировать», внизу — «Скачать» (у Flyway — «Скачать оба файла»: два файла подряд через `downloadBlob`).
- Состояния доски читаются при открытии окна: текст, который участник копирует, не меняется под рукой от правок других.
  Открыть заново — прочитать снова.
- Сравнение версии: из снимка версии в снимок живой доски; кнопка — в шапке просмотра версии, пока включено «Сравнить
  с текущей».
- Предложение: из живой доски в доску, какой её сделает «Принять»: копия документа доски, в которую `mergeProposal`
  сливает разницу основы и черновика (`mergedSnapshot` в `diagram/merge.ts`), — ровно то, что получит база, если
  принять предложение сейчас. Альтернативы отклонены: «основа → черновик» не учитывает правок доски после предложения
  (переименованное на доске поле миграция назвала бы старым именем), а «доска → черновик» откатила бы правки доски,
  которых предложение не касалось.
- Кнопка доступна всем, кто видит сравнение (владелец и редакторы — в истории версий, автор и проверяющие — в
  предложении): генерация ничего не меняет и не уходит в сеть.

## Risks / Trade-offs

- [База отличается от доски] → генератор не видит базы: имена ограничений, созданные не PostgreSQL по умолчанию и не
  этим генератором, не совпадут. Заголовок SQL говорит, из какого состояния в какое миграция; имена — как у выгрузки
  `schemaSql`.
- [Сопоставление по имени ошибается] → таблица удалена и нарисована заново с тем же именем, но другим смыслом, —
  получится `ALTER`, а не `DROP` + `CREATE`. Это безопаснее для данных, а оператор виден в предпросмотре.
- [Синтаксис старых версий СУБД] → `RENAME COLUMN` требует MySQL 8.0, MariaDB 10.5.2, SQLite 3.25; `DROP COLUMN` —
  SQLite 3.35. Это версии 2018–2021 годов; старые требуют `CHANGE COLUMN` и пересоздания таблиц.
