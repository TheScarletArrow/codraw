# Design

## Context

«Миграция SQL» (`sql/migration.ts`) строит `BoardSchema` каждого состояния доски через `boardSchema` → `diagramTables`,
сопоставляет таблицы, поля и индексы по ключам `<страница>/<элемент>` (`match`), а `Planner` раскладывает разницу на
шаги `Operation` с фазами безопасного порядка (`PHASE`), которые `SqlDialect.render` из `sql/dialects.ts` пишет для
одной из шести СУБД; шаг, которого СУБД не умеет, — комментарий с `unsupported`. Обратная миграция — тот же генератор
из нового состояния в старое; Flyway и Liquibase собираются из обеих (`migrationFiles.ts`).

Представление на доске (`add-database-views`) — таблица с ключами стиля `codrawView`, `codrawViewMaterialized` и
`codrawViewQuery`. `diagramViews` (`sql/erDiagram.ts`) читает их в `SqlView` — имя, столбцы из полей, запрос, признак,
индексы материализованного, зависимости из запроса, — но без идентификаторов элементов, а `diagramTables` их
пропускает, поэтому миграции представлений не видят. `schemaSql` уже пишет их в порядке зависимостей (`viewOrder`).

## Goals / Non-Goals

**Goals:**

- Миграция создаёт, снимает, переименовывает и заменяет представления и индексы материализованных между двумя
  состояниями доски для всех шести СУБД, а порядок операторов выполним: базы не дают менять то, что читает
  представление.
- Flyway и Liquibase с откатом получают это без отдельного кода.

**Non-Goals:**

- Перевод запроса между диалектами: запрос пишется, как на доске (как и в «Скопировать SQL»).
- Разбор запроса для поиска столбцов, которые он читает: представление снимается при любом удалении столбца или смене
  типа в таблице, которую оно читает.
- `ALTER VIEW … RENAME COLUMN`, `WITH CHECK OPTION`, права на представления, `REFRESH MATERIALIZED VIEW`, индексированные
  представления SQL Server и `TO`-таблицы материализованных представлений ClickHouse.
- Изменения окна «Миграция SQL»: сводка и предпросмотр те же.

## Decisions

### Представления в схеме состояния

- `erDiagram.ts` получает `diagramViewCells(cells): DiagramView[]` — представление страницы с идентификатором ячейки и
  идентификаторами строк индексов (`DiagramIndex`), как `diagramTables`; `diagramViews` остаётся тем же и берёт
  `view` из него. Альтернатива — второй разбор ячеек в `migration.ts`: отклонено, правила чтения полей и индексов
  разошлись бы.
- `BoardSchema.views: SchemaView[]` — `SqlView` с ключом `<страница>/<элемент>` и индексами `SchemaIndex` с ключами.
  Таблицы и представления делят пространство имён, как в базах: схема сначала берёт таблицы всех страниц, затем
  представления; представление с именем таблицы или более раннего представления не берётся и попадает в
  `repeatedViews`, а файл начинается с комментария о нём (у таблиц — прежний `repeated`).
- Таблица, ставшая представлением (тот же элемент, «Представление»), — удалённая таблица и новое представление:
  сопоставление идёт внутри таблиц и внутри представлений.

### Операции и возможности СУБД

- Новые `Operation`: `createView { view: { name, materialized, query }, replace }`, `dropView { view, materialized }`,
  `renameView { from, to, materialized }`. `SqlDialect.views` — что СУБД умеет: `replace` (замена запроса на месте),
  `rename`, `materialized`, `renameMaterialized`. Планировщик выбирает между переименованием, заменой и пересозданием
  по этим признакам, как выбирает по `renames` для ограничений.

  | СУБД        | переименование               | замена                 | материализованные                         |
  |-------------|------------------------------|------------------------|-------------------------------------------|
  | PostgreSQL  | `ALTER [MATERIALIZED] VIEW`  | `CREATE OR REPLACE`    | да, индексы                               |
  | MySQL       | `RENAME TABLE`               | `CREATE OR REPLACE`    | нет — комментарий                         |
  | Oracle      | `RENAME` (материализованное — пересоздание) | `CREATE OR REPLACE` | да, индексы                  |
  | SQL Server  | пересоздание                 | `CREATE OR ALTER`      | нет — комментарий                         |
  | SQLite      | пересоздание                 | нет — пересоздание     | нет — комментарий                         |
  | ClickHouse  | `RENAME TABLE`               | `CREATE OR REPLACE`    | `ENGINE = MergeTree ORDER BY tuple() POPULATE` |

- SQL Server: `sp_rename` не меняет текст определения в `sys.sql_modules`, и Microsoft советует снять и создать
  представление; `CREATE VIEW` должен начинать пакет, поэтому создание — `EXEC(N'CREATE [OR ALTER] VIEW …');`, которое
  выполняется в любом месте файла, без `GO`.
- ClickHouse: материализованное представление — триггер вставки с собственной таблицей; без `TO` ему нужен движок.
  Миграция пишет `ENGINE = MergeTree`, `ORDER BY tuple()` и `POPULATE` (строки, что уже есть) и комментарий, что движок
  и ключ сортировки стоит подобрать под запрос, а строки, вставленные во время `POPULATE`, в представление не попадут.
  Индексы ClickHouse по-прежнему — комментарий.
- Представление без запроса: `dialect()` пишет `createView` с пустым запросом комментарием `unsupported` одинаково для
  всех СУБД, до вызова её функции.

### План представлений

Для пар представлений (`match` по ключам, затем по имени):

1. Своё изменение: признак «Материализованное» или запрос (сравнение после схлопывания пробелов). Если в новом состоянии
   запроса нет — шаг-комментарий без снятия. Иначе обычное представление, у которого СУБД умеет замену, а прежние поля —
   начало новых с теми же именами и типами (`sameType`), заменяется; остальное пересоздаётся.
2. Имя изменилось, и представление не пересоздаётся: переименование, если СУБД умеет его для этого вида; иначе
   пересоздание (без запроса — шаг-комментарий).
3. Пересоздание из-за таблиц: представление старого состояния снимается, когда его зависимость — таблица, которая
   удаляется, теряет столбец или меняет тип столбца, или снимаемое представление (замыкание по зависимостям). Такое
   представление создаётся заново, если оно есть в новом состоянии, — без запроса комментарием.
4. Индексы материализованного представления, которое остаётся и не пересоздаётся, планирует тот же `planIndexes`, что и
   индексы таблиц, на паре «таблиц» с именами представлений и без столбцов: снятие, пересоздание при изменении,
   переименование. Новое и пересоздаваемое материализованное представление создаётся вместе со всеми индексами, снятое —
   теряет их вместе с собой. Для СУБД без материализованных представлений индексы не планируются.

Альтернатива для пункта 1 — замена всегда, где СУБД её умеет без ограничений на столбцы (MySQL, Oracle, SQL Server,
ClickHouse): отклонено ради одного правила для всех СУБД, как в задаче; снятие и создание обычного представления не
теряет данных.

Почему переименования таблиц и столбцов не пересоздают представления: PostgreSQL сам переводит представление на новое
имя, а запрос на доске текст не меняет; если запрос на доске поправили, он даёт замену. Пересоздание по старому тексту
запроса сломало бы работающее представление.

### Порядок

- `PHASE.dropViews = -1` — раньше всего: представления снимаются в обратном порядке зависимостей старого состояния
  (читающее — раньше читаемого). `PHASE.createViews = 8` — после внешних ключей: создание и замена в порядке
  зависимостей нового состояния, у каждого материализованного сразу его индексы. Порядок зависимостей — `viewOrder` из
  `erDiagram.ts`, обобщённый на всё, у чего есть `name` и `dependencies`, и экспортируемый.
- Переименования таблиц и представлений — один список `orderRenames` в фазе переименования таблиц: имена общие, и
  переименование таблицы в имя, которое освобождает представление, ждёт его. Временные имена ограничений и индексов
  обходят и имена представлений с их индексами.

### Опасность

- `DROP MATERIALIZED VIEW` удалённого представления — с `ВНИМАНИЕ`: его строки пропадают вместе с ним. Снятие
  обычного представления и снятие перед созданием заново — не опасно: строки считаются запросом снова.

## Risks / Trade-offs

- [Поля представления на доске не совпадают с тем, что даёт запрос (запрос поправили, а поля — нет)] → замена в
  PostgreSQL упадёт на смене столбцов; README говорит держать поля в согласии с запросом, а импорт и «Подключиться к
  базе…» ставят их из запроса.
- [Пересоздание при любом удалении столбца или смене типа читаемой таблицы, даже не того столбца] → лишние
  `DROP`/`CREATE` и пересчёт материализованного представления; зато миграция выполнима без разбора запроса.
- [Переименование таблицы или столбца ломает представление в MySQL, Oracle и SQL Server, если запрос на доске не
  поправили] → поправленный запрос даёт замену после переименования; README говорит об этом.
- [Права на пересозданное представление теряются] → как при любом `DROP`/`CREATE`; README упоминает.
- [Запрос не переводится между диалектами] → как и в выгрузке SQL.
