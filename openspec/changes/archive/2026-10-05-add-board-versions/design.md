# Design

## Context

Состояние документа доски — бинарное состояние Yjs в `board_documents.state`, одна строка на доску. `collab` держит
живой документ в памяти и сохраняет его через `PUT /internal/boards/{id}/document` не позже чем через 10 секунд после
изменения; `backend` перезаписывает строку и обновляет `boards.updated_at`. Модель документа (`meta`, `pages`,
`cells:<pageId>` — вложенные Y.Map) знает только фронтенд; для `backend` состояние непрозрачно. Требования —
в `specs/`.

## Goals / Non-Goals

**Goals:**

- Версии появляются без участия клиентов: их делает `backend` при сохранении документа.
- Восстановление не ломает совместную работу: подключённые участники получают его как обычную правку и продолжают
  работать без переподключения.
- Восстановление обратимо: состояние перед ним остаётся в истории.

**Non-Goals:**

- Названия версий, сравнение версий, восстановление отдельной страницы или фигуры.
- История для участников, которые не владеют доской.
- Хранение версий во внешнем хранилище (S3) и прореживание старых версий по времени.

## Decisions

### Хранение

```
board_versions (id uuid PK DEFAULT uuidv7(), board_id uuid → boards ON DELETE CASCADE, state bytea NOT NULL,
                reason text NOT NULL CHECK (reason IN ('AUTO', 'MANUAL', 'RESTORE')), created_at timestamptz NOT NULL)
INDEX (board_id, created_at DESC)
```

- Полная копия состояния, а не разница: состояние Yjs само сжато, а разницу пришлось бы собирать в `backend`, который
  модель документа не знает. Предел — 100 версий на доску: после вставки удаляются версии старше сотой
  (`DELETE … WHERE id IN (SELECT … OFFSET 100)`). При удалении доски версии уходят каскадом.
- Значения `reason` в базе — имена enum, в API — в нижнем регистре, как у `linkAccess`.

### Когда появляется версия

- В `BoardDocumentService.save`, в той же транзакции, что и запись документа: если последней версии доски нет или она
  старше 10 минут, а у доски уже есть сохранённое состояние, это прежнее состояние сохраняется как версия `AUTO`, затем
  записывается новое. Так версия — это доска перед первой правкой после паузы, а при непрерывной работе — снимок не
  реже раза в 10 минут.
- Альтернатива — сохранять новое состояние. Отклонено: после паузы участник может сразу всё стереть, и версия стёртой
  доски бесполезна, а состояние до правки уже потеряно.
- Альтернатива — версии по таймеру в `collab`. Отклонено: `collab` знает только загруженные документы, а `backend`
  видит каждое сохранение в одном месте и в транзакции.
- Последняя версия ищется по индексу `(board_id, created_at DESC)` — одна строка; документ при этом читается только
  когда версию действительно нужно сохранить (`INSERT … SELECT state FROM board_documents`), без лишней передачи
  мегабайтов.

### API

- `GET /api/boards/{id}/versions` → `[{id, createdAt, reason}]`, новые первыми; `GET …/versions/{versionId}` →
  `application/octet-stream`; `POST …/versions?reason=manual|restore` с телом `application/octet-stream` → 201 и
  версия. Только владелец: остальным 403, как для переименования. Версия ищется по паре (доска, версия) — версия
  чужой доски даёт 404.
- Ручная версия принимает состояние от клиента, а не берёт сохранённое: сохранённое отстаёт от живого документа на
  время задержки `collab` (до 10 секунд), и правки последних секунд перед восстановлением потерялись бы. Владелец и так
  может записать в свою доску что угодно правками, поэтому новое право не появляется. Тело — от 1 байта до 16 МБ.
- `reason=auto` через API не принимается: автоматические версии делает только `backend`.

### Восстановление

- Восстанавливает страница владельца: загружает состояние версии в отдельный `Y.Doc` и одной транзакцией с отдельным
  `origin` приводит живой документ к его содержимому. Обход общий для всех верхних карт документа (`meta`, `pages`,
  `cells:*`): ключи, которых нет в версии, удаляются; вложенные Y.Map сравниваются рекурсивно; простые значения
  записываются, только если отличаются; карты страниц, которых нет в версии, очищаются (верхний тип Yjs удалить
  нельзя, так же поступает удаление страницы).
- Почему не заменить документ на сервере: живой документ в памяти `collab` перезаписал бы такую замену при следующем
  сохранении, а принудительная перезагрузка документа разорвала бы соединения участников. Правка, напротив, доходит до
  всех как любая другая и сливается с их одновременными правками по правилам CRDT.
- Почему минимальная разница, а не «очистить и записать заново»: неизменённые фигуры остаются теми же объектами Yjs,
  поэтому их одновременные правки другими участниками не теряются, а правка меньше.
- Перед правкой страница сохраняет текущее состояние живого документа как версию `restore`; если сохранить не удалось,
  восстановление не выполняется.
- `origin` восстановления не отслеживают менеджеры undo страниц: отменить его через Ctrl+Z нельзя, вернуть прежнее
  состояние можно восстановлением версии «Перед восстановлением».

### Интерфейс

- «История версий» — пункт меню доски на её странице (только у владельца). Справа открывается панель: «Сохранить
  версию», список версий (время, вид) и «Закрыть».
- Выбранная версия показывается вместо живого холста: свои вкладки страниц и холст только для чтения на отдельном
  `Y.Doc`, без публикации присутствия — участники не видят курсор владельца на странице, которой у них нет. Над холстом —
  время версии, «Восстановить эту версию» (с подтверждением) и «Закрыть». Живой документ всё это время синхронизируется.

## Risks / Trade-offs

- [Рост базы: до 100 копий документа на доску] → копия обычной доски — десятки килобайт; предел ограничивает рост;
  прореживание по времени — следующий шаг, если понадобится.
- [Сотая версия вытесняет нужную при очень долгой работе] → 100 версий — не меньше 16 часов непрерывной работы при
  интервале 10 минут; перед восстановлением и вручную версии сохраняются сверх интервала.
- [Участник правит доску во время восстановления] → его правки сливаются с восстановлением; правка фигуры, которую
  восстановление удалило, теряется, как при одновременном удалении фигуры другим участником.
- [Злонамеренный клиент с правом правки стирает доску] → это и есть сценарий восстановления; для посторонних есть
  режимы доступа по ссылке.

## Migration Plan

1. Пара миграций V5/U5: таблица `board_versions` и индекс; U5 удаляет таблицу.
2. Выкатить `backend`, затем `frontend`. Версии начинают появляться с первого сохранения документа после выката.
3. Откат — U5 и предыдущие версии сервисов; версии теряются, документы досок не затрагиваются.
