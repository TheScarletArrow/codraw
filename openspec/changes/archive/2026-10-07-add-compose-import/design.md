# Design

## Context

Импорты живут в меню «SQL и Mermaid» (`sql/SqlMenu.tsx`): окно с текстом и файлами, сводка, «Добавить на страницу».
Образец ближе всего — «Импорт OpenAPI / AsyncAPI…» (`apiSpec/`): `loadDocument.ts` разбирает JSON и YAML с лениво
загружаемой библиотекой `yaml`, пределом 5 МБ и ошибкой «файл: строка, столбец — причина»; ячейки строит
`DiagramBuilder` из фигур палитры, раскладывает `layoutShapes` (ELK, ADR-0003) — он умеет и рамки: фигура с
`frame: true` и известными детьми (`parent`) становится составным узлом и растягивается вокруг них; место справа даёт
`placeBeside`, а `editor.insertCells` добавляет всё одним шагом отмены и отмечает участника. Таблица — только фигура
со `stackLayout`, поэтому обычные фигуры палитры в выгрузку SQL не попадают сами собой.

## Goals / Non-Goals

**Goals:**

- Из одного или нескольких файлов compose получить редактируемую схему контейнеров: узнаваемые фигуры, зависимости,
  сети.
- Основа для следующего импорта инфраструктуры (Kubernetes, #97): тот же граф, те же ячейки и окно.

**Non-Goals:**

- Полная модель compose: `extends`, `include`, `secrets`, `configs`, тома, `deploy`, подстановка из `.env`.
- Свойства элементов (технология, теги) — их ещё нет (#82); образ пишется в подпись.

## Decisions

### Граф инфраструктуры между разбором и ячейками

Разбор compose (`infra/parseCompose.ts`) даёт проект — сервисы со всеми нужными полями; `infra/composeGraph.ts`
превращает его в граф инфраструктуры `InfraGraph`: узлы (фигура палитры, строки подписи, рамка), рамки (фигура,
подпись) и связи (концы, подпись). `infra/infraCells.ts` строит из графа ячейки и раскладывает их. Окно
`infra/InfraImport.tsx` знает только о графе и сводке. Так импорт Kubernetes добавит свой разбор и свой граф, не
трогая ячейки и раскладку. Альтернатива — строить ячейки прямо из проекта compose, как `apiSpecCells` строит их из
спецификаций, — проще сейчас, но вторая такая же функция для Kubernetes повторила бы размеры фигур, рамки и раскладку.

### Разбор и слияние файлов

- Документ — `loadDocument` из `apiSpec/` как есть: файл compose — один документ YAML, ошибки и пределы те же.
- Документ без объекта `services` — ошибка «это не docker-compose — нет раздела services»; пустой `services` — проект
  без сервисов, кнопка недоступна.
- Поля сервиса читаются в краткой и полной форме: `depends_on` списком или словарём, `build` строкой или объектом
  (`context`, `dockerfile`), `ports` строками, числами или объектами (`published`), `environment` списком `KEY=VALUE`
  или словарём, `networks` списком или словарём (с `aliases`).
- Слияние — упрощённые правила compose: следующий файл заменяет `image`, `build`, `network_mode`, `container_name` и
  `hostname`, добавляет без повторов `depends_on`, `links`, `networks`, псевдонимы и порты, а переменные окружения
  сливает по имени. Порядок — файлы в порядке выбора, затем текст поля, как в импорте OpenAPI.

### Переменные

Compose подставляет переменные из окружения и `.env`, которых у браузера нет. `${ИМЯ:-x}` и `${ИМЯ-x}` берут `x`:
файл сам говорит, каким будет значение без настройки (`${CODRAW_HTTP_PORT:-8080}` → `8080`); `${ИМЯ}`, `$ИМЯ` и
`${ИМЯ:?текст}` пишутся как `${ИМЯ}` — так подпись не теряет того, что значение задают при запуске; `$$` — `$`.
Подставляется в образ, порты и значения переменных окружения.

### Фигура по образу

Имя образа без реестра (первая часть пути с точкой, двоеточием или `localhost`), тега и дайджеста делится на слова по
`/`, `.`, `_`, `-`; категория выбирается по первому совпавшему слову в порядке: инструменты при сервисе (`ui`,
`exporter`, `admin`, `commander`, `express`, `console`, `dashboard` → «Контейнер»: `kafka-ui` — не Kafka,
`redis_exporter` — не Redis), базы данных, кэши, очереди, топики, балансировщики, шлюзы, хранилища объектов, поиск,
хранилища данных. Слова — по образам из Docker Hub и официальных реестров (`postgres`, `postgresql`, `postgis`,
`timescaledb`, `mysql`, `mariadb`, `mongo`, `mongodb`, `mssql`, `oracle`, `cockroach`, `cassandra`, `scylla`, `couchdb`,
`neo4j`; `redis`, `valkey`, `keydb`, `dragonfly`, `memcached`; `rabbitmq`, `activemq`, `artemis`, `nats`, `mosquitto`;
`kafka`, `redpanda`, `pulsar`; `nginx`, `haproxy`, `traefik`, `envoy`, `caddy`; `kong`, `krakend`, `tyk`, `apisix`;
`minio`, `rustfs`, `seaweedfs`, `azurite`; `elasticsearch`, `opensearch`, `solr`, `meilisearch`, `typesense`;
`clickhouse`, `druid`). Целые слова, а не подстроки: `pgadmin4` не база данных. Отдельный список, а не поиск фигур
палитры (`shapeSearch.ts`): поиск ищет по началу слова и по общим словам («api», «app»), а импорту нужен однозначный и
проверяемый тестами ответ.

### Подпись и размеры

Строки подписи — имя, образ (без него — `./каталог` сборки, а при `dockerfile` — путь к Dockerfile от каталога сборки),
порты `:опубликованный` через запятую (`"127.0.0.1:9090:9090"` → `:9090`, `8000-8010:8000-8010` → `:8000-8010`, порт
без публикации не пишется). Ширина фигуры с подписью внутри — по самой длинной строке (7,5 px на знак, как в импорте
OpenAPI), не меньше фигуры палитры и не больше 560 px; высота — по числу строк. У фигур с подписью под фигурой
(`verticalLabelPosition=bottom`: «Хранилище объектов», «Топик событий») сама фигура не растягивается, а раскладке
отдаётся рамка «фигура и подпись под ней», и фигура ставится по центру её верха — подпись не налезает на соседей.

### Связи

- Направление — от зависимого к зависимости, как стрелка вызова на схемах: `backend -> postgres`.
- Связи по переменным: значение ищется на имя, `container_name`, `hostname` и псевдонимы других сервисов как адрес:
  `схема://[пользователь@]хост` (с `jdbc:`), `хост:порт` в начале значения или после пробела, запятой, точки с запятой
  или `=`, либо значение целиком. Подпись — протокол по схеме (таблица в спецификации), без схемы — пустая. Это
  эвристика: значение `POSTGRES_USER=postgres` у другого сервиса тоже даст связь — поэтому галочка, которую можно снять.
- Связь из `depends_on` и связь из переменной между теми же сервисами в ту же сторону — одна связь с подписью
  протоколов.

### Сети

Рамки рисуются, только когда сетей хотя бы две: одна рамка вокруг всего ничего не говорит. Сеть сервиса — первая из
его `networks`, иначе `default`; рамка — фигура «Граница» с именем сети, родитель её сервисов для раскладки. Сервис в
нескольких сетях попадает в рамку первой — у фигуры в CoDraw одна рамка.

### Фигуры C4

С галочкой база данных — Database C4, остальное — Container C4 (C4 различает только хранилище данных и контейнер),
подпись — имя, `[Container: образ или сборка]` и порты третьей строкой, на месте описания. Рамки сетей остаются
«Границами»: граница C4 — это граница системы, а не сети.

### Пределы

Файл — до 5 МБ (как у импорта API); сервисов — до 300 за раз: больше — сводка и ошибка «Слишком много сервисов: N».

## Risks / Trade-offs

- [Эвристика связей по переменным даёт лишнюю связь, если имя сервиса совпадает с обычным значением] → галочка
  «Связи по переменным окружения» и подпись протоколом, по которой лишнюю связь видно; правится как любая связь.
- [Сервис в нескольких сетях виден только в одной рамке] → поведение описано в спецификации; полная картина сетей —
  после свойств элементов (#82), где сети станут метками.
- [Неизвестный образ становится «Контейнером»] → это честный ответ, фигуру можно заменить; список слов дополняется
  без изменения поведения остальных.
