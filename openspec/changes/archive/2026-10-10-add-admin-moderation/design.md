## Context

Пользователи CoDraw входят через GitHub, Google или гостем (`users.provider` = `github`, `google`, `guest`); сеансы
хранит Spring Session JDBC (`spring_session`), и имя принципала сеанса — id пользователя. `collab` пускает в документ по
короткому (5 минут) токену `backend` и спрашивает права у внутреннего API (`GET /internal/boards/{id}/access`) при
подключении и раз в минуту у открытых документов; закрыть подключение по инициативе `backend` сейчас нельзя — `collab`
сам ходит в `backend`, а не наоборот. Без входа открыты доска в режиме `public` (`/api/public/boards/**`), её картинки
и живая картинка `/api/embeds/{ключ}.svg`. Корзина досок уже есть (`BoardService.moveToTrash`, 30 дней). Роли
администратора установки нет вовсе: правила безопасности знают только «вошёл / не вошёл».

## Goals / Non-Goals

**Goals:**

- Администраторы только из конфигурации, проверка прав в `backend` на каждый запрос.
- Блокировка, которая действует сразу: вход, сеансы, токены и подключения `collab`.
- Закрытие публичного доступа к доске, которое владелец не может тут же отменить.
- Жалобы читателей без входа с пределом частоты, очередь и журнал действий.

**Non-Goals:**

- Удаление учётной записи администратором: механизм удаления делается в #155, которого ещё нет в `main`; здесь —
  только блокировка. Когда #155 сольют, «Удалить учётную запись» добавит отдельное изменение поверх его сервиса.
- Просмотр содержимого доски администратором: сведения о доске — метаданные; открыть саму доску администратор может, как
  любой посетитель, если её ссылка это позволяет.
- Роли модератора с меньшими правами, назначение администраторов из интерфейса, уведомления владельцу о действиях
  администратора и автоматическое закрытие досок по числу жалоб.
- Капча и хранение сетевых адресов отправителей жалоб.

## Decisions

### Администраторы: `codraw.admin.users` = `провайдер:id`

`CODRAW_ADMINS` (свойство `codraw.admin.users`) — список `github:<числовой id>` и `google:<sub>`. Это те же пары
`(provider, provider_user_id)`, по которым `users` уже уникальны, поэтому запись однозначна, переживает смену логина и
не зависит от того, входил ли администратор раньше. id пользователя (UUID) отвергнут: его нельзя узнать до первого входа,
и он меняется при пересоздании базы. Логин GitHub отвергнут: он меняется и не хранится. Гость (`guest:…`) и неизвестный
провайдер — ошибка запуска (`@Validated` + проверка в `AdminProperties`): у гостя нет внешней учётной записи, которая
подтверждает, кто он.

Как узнать id: GitHub — `https://api.github.com/users/<логин>` (`id`), Google — `sub`, который проще всего взять из
базы после первого входа: `SELECT provider, provider_user_id, name FROM users`. Это в `docs/deploy.md`.

`AdminAccess.isAdmin(userId)` читает пользователя из базы и сверяет пару с множеством из конфигурации. Права не кладутся в
сеанс: убранный из конфигурации администратор теряет их при перезапуске `backend`, а не при истечении сеанса.

### Проверка прав: правило безопасности на `/api/admin/**`

В `SecurityConfiguration` — `authorize("/api/admin/**", access(AdminAuthorizationManager))` перед `anyRequest`: без сеанса
Spring Security отвечает 401 (`HttpStatusEntryPoint`), без прав — 403, и это до контроллера, так что и несуществующий адрес
под `/api/admin/` даёт 403, а не 404. Контроллеры дополнительно берут администратора через `AdminAccess.require`, чтобы
знать его имя для журнала и не полагаться только на путь.

### Блокировка: `users.blocked_at` и удаление сеансов

- Колонка `users.blocked_at timestamptz NULL`. Блокировка — `UPDATE … SET blocked_at = now WHERE blocked_at IS NULL`;
  повторная ничего не меняет и в журнал не пишется.
- Сеансы: `FindByIndexNameSessionRepository.findByPrincipalName(userId)` + `deleteById` для каждого. `JdbcIndexedSession
  Repository` индексирует имя принципала (`PRINCIPAL_NAME` в `spring_session`), а имя принципала у нас — id
  пользователя, и у входа через провайдера, и у гостя. Запрос, который шёл во время блокировки, свой сеанс уже не
  сохранит: Spring Session обновляет строку по id, а её нет.
- Вход: `UserService.signIn(profile)` после upsert бросает `UserBlockedException` для заблокированного;
  `CodrawOAuth2UserService` превращает её в `OAuth2AuthenticationException("account_blocked")`, а обработчик ошибки входа
  ведёт на `/login?blocked` (остальные — на `/login?error`, как раньше). Тестовый вход отвечает 403. Новый гость
  заблокированным не бывает.
- Фильтра, который проверяет блокировку на каждом запросе, нет: без сеанса запросы и так получают 401, а лишний запрос в
  базу на каждый вызов API не нужен. Выдача токена `collab` и `/api/me` — тоже обычные запросы с сеансом.

### Подключения `collab`: `POST /internal/users/blocked`

Внутренний API получает список id и отвечает теми, кто заблокирован: `{"userIds": [...]}` → `{"blocked": [...]}` (до
1000 id за запрос). `collab`:

- при подключении спрашивает о своём пользователе вместе с правами на документ (параллельно) и отказывает с причиной
  `user-blocked` — так закрывается окно в 5 минут, пока действует выданный до блокировки токен;
- раз в 10 секунд (`blockedCheckInterval`) собирает id пользователей всех открытых подключений одним запросом и
  закрывает сокеты заблокированных с кодом 4401 и причиной `user-blocked`; ошибка `backend` подключения не закрывает.

Отвергнутые варианты: добавить список заблокированных в ответ прав доски — проверка шла бы раз в минуту и только по
доскам; вызов `collab` из `backend` — меняет направление связи, требует адреса `collab` в `backend` и не работает при
нескольких экземплярах `collab`. Один лёгкий запрос раз в 10 секунд на экземпляр `collab` дешевле.

Страница доски на `user-blocked` перестаёт подключаться (как при `forbidden`) и перепроверяет сеанс: без сеанса `Layout`
открывает страницу входа.

### Закрытие доступа по ссылке: `boards.sharing_blocked_at`

«Отключить публичный доступ» нельзя свести к смене режима `public` → `view`: гостевой вход свободный, и доска с `view`
или `edit` по ссылке так же доступна любому, кто нажмёт «Продолжить без входа». Поэтому администратор закрывает доступ по
ссылке целиком:

- в одной транзакции: `link_access = 'NONE'`, удаление строки `board_embeds` (адрес живой картинки — 404, новый ключ при
  будущем включении), `sharing_blocked_at = now`, запись в журнал, отбрасывание посещений тех, кто потерял доступ
  (`forgetUsersWithoutAccess`, как при обычной смене режима);
- пока стоит запрет, `BoardService.changeLinkAccess` и `EmbedController.enable` отвечают 409 (`SharingBlockedException`,
  `title` «Sharing blocked») на всё, кроме `none`; `shownWithoutSignIn` и `Embeds.image` дополнительно проверяют, что
  запрета нет, — на случай гонки с владельцем, сменившим режим за миг до запрета;
- ответ доски получает `sharingBlocked`, окно «Поделиться» показывает владельцу причину;
- `collab` узнаёт о новом режиме при следующей проверке прав (раз в минуту) или сразу, если владелец открыт и получит
  `board-changed`; для подключений по ссылке это та же смена режима, что и у владельца.

Снятие запрета ставит `sharing_blocked_at = NULL` и больше ничего: администратор не знает, какой режим владелец хотел бы
вернуть.

### Корзина

`AdminService.moveToTrash` вызывает существующий `BoardService.moveToTrash` от имени владельца доски: доска пропадает
отовсюду, владелец видит её в корзине и может восстановить за 30 дней. Окончательного удаления администратором нет —
восстановление владельцем страхует от ошибки администратора, а запрет доступа по ссылке после восстановления остаётся.

### Жалобы

- `POST /api/public/boards/{id}/reports` открыт без входа (`permitAll` для `POST` этого шаблона) с CSRF, как отчёты об
  ошибках браузеров: страница просмотра получает cookie токена первым же запросом.
- Принимается только доска, которую показывает `shownWithoutSignIn` (иначе 404 — адрес по-прежнему ничего не говорит о
  закрытых досках). Предел — `AddressRateLimiter` на адрес, 5 в час (`codraw.limits.reports-per-address-per-hour`), 429 с
  `Retry-After`; сверх `codraw.limits.reports-per-board` (50) открытых жалоб на доску жалоба не сохраняется, но ответ тот
  же 204: доска уже в очереди, а отказ подсказал бы спамеру, что можно перестать.
- Таблица `board_reports`: `id`, `board_id` (FK, `ON DELETE CASCADE`), `reason` (CHECK), `message` (до 1000),
  `reporter_id` (FK `ON DELETE SET NULL`), `created_at`, `resolved_at`, `resolved_by` (FK `SET NULL`), `resolved_by_name`.
  Адрес не хранится: в журнале `backend` он и так есть по строке запроса, а предел держит его в памяти час.

### Журнал

Таблица `admin_actions`: `id`, `admin_id` (без FK), `admin_name`, `action` (CHECK: `block_user`, `unblock_user`,
`block_sharing`, `unblock_sharing`, `trash_board`, `resolve_report`), `target_kind` (`user`, `board`, `report`),
`target_id`, `target_label`, `details` (необязательный текст, например число закрытых жалоб), `created_at`. Без внешних
ключей и с копиями имён: журнал должен пережить удаление и администратора, и цели (в том числе уборку гостей и будущее
удаление учётных записей #155). Запись делается в той же транзакции, что и действие, поэтому не удавшееся действие следа
не оставляет. Чтение — `GET /api/admin/actions?before=<время>` страницами по 100.

### Срок хранения

`codraw.admin.retention` (`CODRAW_ADMIN_RETENTION`, по умолчанию 365 дней): уборка раз в час (`codraw.admin.cleanup-cron`)
удаляет записи журнала и закрытые жалобы старше срока пачками, как уборка уведомлений. Год — компромисс между разбором
повторных нарушений и минимизацией данных; срок попадает в `/api/legal` (`adminRetentionDays`) и политику.

### Размер доски в сведениях

Сумма `octet_length(state)` документа, `sum(octet_length(state))` версий и `sum(size)` картинок — по запросу одной доски,
не в поиске, чтобы список не считал размеры всех досок.

### Frontend

- `/admin` — ленивый маршрут внутри `Layout`; ссылка «Администрирование» (иконка щита) в меню пользователя только при
  `me.admin`. Не администратор видит «Нет доступа» (по `me.admin` и по 403 от API).
- Вкладки: «Жалобы» (открытые, группа по доске: «Сведения», «Закрыть»), «Пользователи» (поиск, «Заблокировать» с
  подтверждением `confirm`, «Разблокировать»), «Доски» (поиск, сведения в боковой панели с действиями), «Журнал».
- `/view/{id}`: кнопка «Пожаловаться» в шапке открывает поповер с формой (Radix Popover уже в зависимостях).
- «Поделиться»: при `sharingBlocked` — сообщение, режимы кроме «Только участники» и живая картинка недоступны.
- `LoginPage`: при `?blocked` — «Учётная запись заблокирована администратором установки».

### Миграция

`V28__claude_admin_moderation.sql` / `U28__…`: две колонки, две таблицы и индексы (`board_reports (board_id) WHERE
resolved_at IS NULL`, `board_reports (created_at)`, `admin_actions (created_at)`, `users (lower(name))` не нужен —
поиск по `ILIKE` на сотнях и тысячах пользователей). Откат удаляет таблицы и колонки; закрытые администратором доски
остаются с режимом `none`. Номер — следующий свободный в `main` на момент открытия PR.

## Risks / Trade-offs

- [Проверка блокировки в `collab` раз в 10 секунд] → лишний запрос к `backend` на экземпляр `collab`; запрос один на все
  подключения, по первичному ключу, и не идёт, когда подключений нет.
- [Права администратора читаются из базы на каждом запросе к `/api/admin/**`] → один запрос по первичному ключу; раздел
  администрирования — редкие запросы.
- [Администратор ошибся с закрытием или корзиной] → снятие запрета и восстановление из корзины владельцем; журнал
  показывает, кто это сделал.
- [Предел жалоб в памяти] → после перезапуска или при нескольких экземплярах `backend` адрес отправит больше; как и у
  гостей и отчётов об ошибках, этого достаточно против случайного потока, а предел на доску держит размер очереди.
- [Блокированный гость создаёт нового гостя] → новые гости ограничены пределом на адрес; против этого — закрытие доступа
  к его доскам и корзина.

## Migration Plan

Миграция только добавляет: существующие доски без запрета, пользователи не заблокированы. Без `CODRAW_ADMINS`
администраторов нет, и установка работает, как раньше. Откат — `U28`, затем предыдущий образ.
