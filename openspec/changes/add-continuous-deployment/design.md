## Context

CoDraw разворачивается на одном сервере из `docker-compose.prod.yml` и `.env.prod` (`docs/deploy.md`). CI при каждом
пуше собирает четыре образа, поднимает из них стек, проверяет его в браузере, резервные копии и оповещения; в `main`
публикует образы с тегом коммита, а задача `release` после всех проверок ставит `latest`. Обновление — `docker compose
pull` и `up -d --wait`; откат — `CODRAW_VERSION=<прежний коммит>`. `docker-compose.prod.yml` и `deploy/prometheus`,
`deploy/alertmanager` оператор копирует на сервер руками, а `.env.prod` с секретами живёт только там. Схему базы
`backend` мигрирует при старте (Flyway), а миграции, которых старый `backend` не знает, Flyway по умолчанию
пропускает (`ignoreMigrationPatterns = *:future`), поэтому прежний образ стартует на новой схеме, если та совместима.

## Goals / Non-Goals

**Goals:**

- Каждый коммит `main`, прошедший все проверки, сам доходит до сервера, и в той же задаче видно, удалось ли.
- Выкатка ничего не ломает, если может упасть до переключения: файлы, образы, переменные и резервная копия
  проверяются заранее.
- Неудачная выкатка сама возвращается к прежней версии.
- Никаких постоянных секретов GitHub на сервере и секретов сервера в GitHub, кроме ключа SSH.

**Non-Goals:**

- Несколько серверов, Kubernetes, blue-green и выкатка без простоя: стек — один сервер, а `collab` держит документы
  в памяти; на время перезапуска участники видят «Нет связи» и переподключаются сами, как и при ручном обновлении.
- Стенд перед продакшеном (staging): его можно добавить вторым Environment той же задачи.
- Откат миграций базы: U-скрипты остаются ручными (`docs/deploy.md`).
- Управление `.env.prod` из CI.

## Decisions

### Push по SSH из GitHub Actions

Задача `deploy` заходит на сервер по SSH и запускает там скрипт. Альтернативы:

- **Pull на сервере** (таймер systemd или Watchtower следит за `latest`): серверу не нужен входящий SSH, но
  результат выкатки не виден в GitHub, файлы `docker-compose.prod.yml` и `deploy/` так не обновить, а Watchtower
  обновляет контейнеры по одному, без `--wait`, резервной копии и отката.
- **Self-hosted runner на сервере**: не нужен SSH, но на продакшене живёт процесс, который выполняет задачи из
  репозитория и держит сокет Docker, а обновлять и охранять его — отдельная работа.

SSH проще, результат и журнал — в задаче, а ключ хранится в секретах Environment. ADR-0016.

### Задача `deploy`

```yaml
deploy:
  if: github.ref == 'refs/heads/main'
  needs: [release]
  environment: production
  concurrency: { group: production, cancel-in-progress: false }
  permissions: { contents: read, packages: read }
```

- `needs: release` — выкатка идёт только после всех проверок коммита и после того, как `latest` указал на него.
- `environment: production` — переменные и секреты выкатки живут в Environment, а оператор может включить там
  «Required reviewers» и подтверждать каждую выкатку или ограничить ветки.
- `concurrency` без отмены — выкатки идут строго по одной; GitHub держит одну ждущую и вытесняет её более новой, так
  что после серии мержей выкатывается последний коммит.

Переменные Environment: `CODRAW_DEPLOY_HOST`, `CODRAW_DEPLOY_USER`, `CODRAW_DEPLOY_PORT` (22),
`CODRAW_DEPLOY_DIR` (каталог с `.env.prod`), `CODRAW_DEPLOY_PROFILES` (например, `monitoring`), `CODRAW_DEPLOY_URL`.
Секреты: `CODRAW_DEPLOY_SSH_KEY` (закрытый ключ без пароля) и `CODRAW_DEPLOY_KNOWN_HOSTS` (строка `ssh-keyscan`,
проверенная оператором). `StrictHostKeyChecking=yes` и только этот `known_hosts`: подмена сервера не получит ни
кода, ни токена. Без `CODRAW_DEPLOY_HOST` первый шаг пишет `::notice::` и задача проходит, остальные шаги
пропускаются; без остальных обязательных значений она падает и называет их.

### Пакет коммита и скрипт на сервере

Задача упаковывает `docker-compose.prod.yml`, `deploy/prometheus`, `deploy/alertmanager` и `deploy/cd` в tar и
передаёт его по SSH в `<dir>/.codraw-deploy/incoming`, затем вторым вызовом запускает оттуда
`deploy/cd/codraw-deploy deploy <sha>`. Токен задачи для `ghcr.io` идёт скрипту через stdin, а не аргументом: так
его не видно в списке процессов сервера. Скрипт целиком — функция `main`, вызванная последней строкой: bash прочтёт
файл до конца, прежде чем начнёт, и подмена `deploy/cd` по ходу выкатки ему не мешает.

Шаги `codraw-deploy deploy <version>` в каталоге выкатки:

1. Замок `flock` на `.codraw-deploy/lock`: ручной запуск не пересечётся с CI.
2. Прежняя версия — из `.codraw-deploy/version`, а при первой выкатке — тег образа работающего `backend`.
3. `docker compose -f incoming/docker-compose.prod.yml --env-file .env.prod config --quiet` с новой версией и
   профилями: новая обязательная переменная (`${X:?…}`) или ошибка в файле останавливает выкатку здесь.
4. Образы: `config --images` даёт полный список; образы CoDraw новой версии скачиваются `docker --config <tmp>
   pull` с токеном задачи во временной конфигурации Docker (учётные данные сервера в `~/.docker` не меняются, а
   `docker pull` — команда самого Docker, ей не нужны плагины из `~/.docker`), остальные — `docker compose pull
   --ignore-buildable`. Затем каждый образ проверяется `docker image inspect`. `CODRAW_DEPLOY_PULL=0` пропускает
   скачивание (проверка в CI, где образы уже собраны).
5. Резервная копия: если контейнер `backup` работает, — `docker compose exec -T backup codraw-backup now`; неудача
   останавливает выкатку. `CODRAW_DEPLOY_BACKUP=0` пропускает.
6. Переключение: текущие `docker-compose.prod.yml` и каталоги `deploy/…` уходят в `.codraw-deploy/previous`, файлы
   коммита встают на их место; `CODRAW_VERSION=<version> docker compose … up -d --wait --wait-timeout <T> --no-build`.
   `docker-compose.override.yml` рядом, если он есть, подключается вторым `-f`, как велит `docs/deploy.md`.
7. Успех — `.codraw-deploy/version` получает новую версию, образы CoDraw других версий, кроме прежней и `latest`,
   удаляются (`docker image rm` без `-f`: используемые не трогаются). Неудача — откат.

`CODRAW_VERSION` задаётся в окружении команды и перекрывает значение в `.env.prod`, если оператор его там оставил.

### Откат

Если `up --wait` не дождался `healthy` за `CODRAW_DEPLOY_WAIT_TIMEOUT` (300 с), скрипт печатает `docker compose ps`
и хвосты журналов, возвращает файлы из `.codraw-deploy/previous`, поднимает прежнюю версию с `--wait` и выходит с
кодом 1. Не поднялась и она — код 2 и сообщение, что стек требует внимания. Прежней версии нет (первая выкатка) —
откатываться некуда, код 2.

Миграции, которые успел применить новый `backend`, остаются: прежний образ их пропускает. Несовместимое изменение
схемы требует ручного отката U-скриптами — так же, как и сейчас (`docs/deploy.md`).

Откат уже выкаченной версии — «Re-run job» задачи `deploy` у запуска CI нужного коммита: она выкатывает его образы и
его файлы тем же скриптом. `latest` при этом не меняется.

### Проверка приложения после выкатки

`curl` к `<CODRAW_DEPLOY_URL>/api/auth/providers` (200 и JSON) и `/version.json` с повторами до минуты: адрес
проверяет TLS-прокси и nginx, которых `--wait` не видит. Неудача валит задачу, но не откатывает: контейнеры здоровы, и
причина, скорее всего, в прокси. Без `CODRAW_DEPLOY_URL` проверка пропускается с пометкой.

### Проверка скрипта в CI

`deploy/cd/check-deploy.sh` в задаче `images`, после проверок стека и до публикации образов, против того же
поднятого стека (`name: codraw-prod`) из временного каталога выкатки с пустым `.env.prod` (переменные стека уже в
окружении задачи):

1. выкатка образов коммита с `CODRAW_DEPLOY_PULL=0` — успех, `version` равна коммиту, резервных копий на одну больше,
   все контейнеры `healthy`;
2. выкатка тега без образов — отказ до переключения, контейнеры те же;
3. выкатка тега, где `backend` — образ, который сразу завершается, — код 1, после отката `backend` снова на образе
   коммита, все контейнеры `healthy`, файлы и `version` прежние.

## Risks / Trade-offs

- [Ключ SSH в GitHub даёт управление Docker на сервере, а значит и root] → отдельный пользователь и отдельный ключ
  только для CD, `known_hosts` обязателен, Environment с правилами защиты; `docs/deploy.md` это требует.
- [Простой на время перезапуска] → как и при ручном обновлении: «Нет связи» на десятки секунд, вкладки сами
  переподключаются и предлагают обновиться (`add-stale-client-reload`).
- [Миграция без отката] → прежний `backend` пропускает незнакомые миграции; несовместимые изменения схемы и так
  требуют ручного решения, резервная копия перед выкаткой есть.
- [Серия мержей] → выкатывается только последний ждущий коммит; промежуточные остаются опубликованными в реестре.
- [Сервер недоступен] → задача красная, сайт работает на прежней версии; следующий мерж или перезапуск задачи
  выкатит.

## Migration Plan

Без настроенного Environment ничего не меняется. Чтобы включить: пользователь на сервере в группе `docker`,
ключ в `authorized_keys`, каталог выкатки с `.env.prod` (и `docker-compose.override.yml`, если он нужен), переменные
и секреты Environment `production` — по `docs/deploy.md`. Первая выкатка сама положит `docker-compose.prod.yml` и
`deploy/` коммита.
