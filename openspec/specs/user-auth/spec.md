# user-auth Specification

## Purpose

Позволяет пользователям входить в систему через внешних провайдеров или работать гостем, работать под
своим именем и выходить из системы.

## Requirements

### Requirement: Вход через внешнего провайдера

Система SHALL позволять войти через GitHub, Google или корпоративного провайдера OpenID Connect, включённых в
установке, и после успешного входа возвращать пользователя в приложение уже аутентифицированным.

#### Scenario: Успешный вход через GitHub

- **WHEN** пользователь нажимает «Войти через GitHub» и подтверждает доступ у провайдера
- **THEN** он возвращается в приложение, и в шапке отображаются его имя и аватар

#### Scenario: Отказ у провайдера

- **WHEN** пользователь отменяет вход на стороне провайдера
- **THEN** он возвращается на страницу входа с сообщением, что вход не выполнен

### Requirement: Вход гостем

Система SHALL позволять продолжить работу без входа через провайдера: для этого создаётся гостевая
учётная запись с именем вида «Гость N», которая работает со своими досками так же, как пользователь,
вошедший через провайдера.

#### Scenario: Пользователь продолжает без входа

- **WHEN** пользователь нажимает «Продолжить без входа» на странице входа
- **THEN** открывается список его досок, а в шапке отображаются имя «Гость N» и кнопка «Войти»

#### Scenario: Гость снова продолжает без входа

- **WHEN** пользователь с действующим гостевым сеансом нажимает «Продолжить без входа»
- **THEN** новая гостевая учётная запись не создаётся, и он видит свои прежние доски

### Requirement: Срок гостевого сеанса

Гостевой сеанс SHALL действовать 30 дней с последнего обращения и сохраняться после закрытия браузера.
Срок сеанса пользователей, вошедших через провайдера, не меняется.

#### Scenario: Гость возвращается

- **WHEN** гость закрывает браузер и через неделю снова открывает приложение
- **THEN** он работает под тем же именем «Гость N» и видит свои доски

### Requirement: Перенос досок гостя при входе

При входе через провайдера из гостевого сеанса доски гостя и доски, открытые гостем по ссылке, SHALL переходить
пользователю, который вошёл, вместе с личными тегами и папками гостя: папка гостя с именем папки пользователя без
учёта регистра SHALL сливаться с ней, тег, который у пользователя уже есть, SHALL записываться как у пользователя и не
повторяться у доски, а у доски, которую оба положили в папки, SHALL оставаться папка пользователя. Библиотеки фигур
гостя SHALL переходить пользователю со своими компонентами. Пределы тегов, папок и библиотек MUST NOT ограничивать
перенос.

#### Scenario: Гость входит через GitHub

- **WHEN** у гостя есть доска A, и он входит через GitHub
- **THEN** доска A есть в списке досок вошедшего пользователя

#### Scenario: Доски, открытые гостем по ссылке

- **WHEN** гость открыл по ссылке доску X другого пользователя, а затем вошёл через GitHub
- **THEN** доска X есть в ответе `GET /api/boards/shared` для вошедшего пользователя

#### Scenario: Теги и папки гостя

- **WHEN** у пользователя есть папка «Работа» и тег «API», а гость положил доску A в свою папку «работа», дал ей теги
  «api» и «Черновик» и создал папку «Идеи», и гость входит через GitHub
- **THEN** у пользователя папки «Работа» и «Идеи», доска A лежит в «Работа» с тегами «API» и «Черновик», а у гостя
  папок и тегов не остаётся

#### Scenario: Библиотеки гостя

- **WHEN** у гостя библиотека «Эскизы» с компонентом, и гость входит через GitHub
- **THEN** библиотека «Эскизы» с компонентом есть в `GET /api/libraries` вошедшего пользователя

### Requirement: Учётная запись пользователя

Первый вход через провайдера SHALL создавать учётную запись, а повторные входы через того же
провайдера SHALL находить ту же учётную запись и обновлять имя и аватар.

#### Scenario: Повторный вход

- **WHEN** пользователь, уже входивший через GitHub, входит через GitHub снова
- **THEN** он видит свои прежние доски, а имя и аватар соответствуют текущему профилю на GitHub

### Requirement: Доступ к API только после входа

Запросы к `/api/**`, кроме эндпоинтов входа, SHALL без действующего сеанса получать статус 401.

#### Scenario: Запрос без сеанса

- **WHEN** клиент без cookie сеанса запрашивает `GET /api/boards`
- **THEN** ответ имеет статус 401, а фронтенд показывает страницу входа

### Requirement: Защита от CSRF

Изменяющие запросы к `/api/**` SHALL отклоняться со статусом 403, если в них нет действующего
CSRF-токена.

#### Scenario: Запрос без CSRF-токена

- **WHEN** аутентифицированный клиент отправляет `POST /api/boards` без заголовка `X-XSRF-TOKEN`
- **THEN** ответ имеет статус 403, и доска не создаётся

### Requirement: Выход из системы

Система SHALL завершать сеанс по запросу выхода, после чего запросы с прежней cookie получают 401.

#### Scenario: Пользователь выходит

- **WHEN** пользователь нажимает «Выйти»
- **THEN** сеанс завершается, открывается страница входа, а повторный запрос с прежней cookie получает
  401

### Requirement: Профиль текущего пользователя

Система SHALL возвращать по запросу `GET /api/me` идентификатор, имя, аватар текущего пользователя
и признак того, что это гость.

#### Scenario: Пользователь вошёл

- **WHEN** аутентифицированный клиент запрашивает `GET /api/me`
- **THEN** ответ имеет статус 200 и содержит `id`, `name`, `avatarUrl` и `guest`

### Requirement: Удаление брошенных гостей

Система SHALL регулярно, не реже раза в сутки, удалять доски гостей, у которых нет действующего сеанса, если с
доской 30 дней никто не работал: не менял её документ и название и не открывал её по ссылке. Гостя без действующего
сеанса и без досок система SHALL удалять. Гостя, созданного меньше суток назад, и гостя с действующим сеансом
система SHALL не удалять вместе с его досками.

#### Scenario: Гость не вернулся

- **WHEN** сеанс гостя истёк, и с его доской 30 дней никто не работал
- **THEN** доска удаляется вместе с документом и версиями, а затем удаляется и сам гость

#### Scenario: Доску гостя открывают по ссылке

- **WHEN** сеанс гостя истёк, а пользователь B открывал его доску по ссылке неделю назад
- **THEN** доска и гость остаются, и B продолжает работать с доской

#### Scenario: Гость возвращается через месяц работы

- **WHEN** гость с действующим сеансом не менял свою доску больше 30 дней
- **THEN** ни гость, ни доска не удаляются

#### Scenario: Гость вошёл через провайдера

- **WHEN** гость вошёл через GitHub, его доски перешли пользователю, а гостевой сеанс больше не действует
- **THEN** гостевая учётная запись удаляется, а доски пользователя остаются

### Requirement: Предел новых гостей с одного адреса

Система SHALL создавать с одного сетевого адреса не больше 20 гостей в час, если настройка не задаёт другой предел.
Запрос «Продолжить без входа» сверх предела SHALL получать статус 429 с заголовком `Retry-After`, и гость не
создаётся; страница входа SHALL сообщать об этом. Запрос с действующим гостевым сеансом предел не расходует.

#### Scenario: Слишком много гостей

- **WHEN** с одного адреса за час создано 20 гостей, и с него снова нажимают «Продолжить без входа»
- **THEN** ответ имеет статус 429 с `Retry-After`, а страница входа показывает «Слишком много новых гостей с вашего
  адреса. Попробуйте позже или войдите»

#### Scenario: Через час

- **WHEN** с первого из 20 гостей с этого адреса прошёл час
- **THEN** новый гость создаётся

#### Scenario: Другой адрес

- **WHEN** с адреса A создано 20 гостей за час, а с адреса B нажимают «Продолжить без входа»
- **THEN** гость для B создаётся

### Requirement: Согласие с условиями при входе

Страница входа SHALL сообщать, что вход и «Продолжить без входа» означают согласие с условиями использования и
политикой конфиденциальности, со ссылками на страницы `/terms` и `/privacy`.

#### Scenario: Ссылки на странице входа

- **WHEN** посетитель открывает страницу входа
- **THEN** под кнопками входа — строка о согласии со ссылками «условия использования» и «политика
  конфиденциальности», которые открывают эти страницы без входа

### Requirement: Способы входа установки

Страница входа SHALL показывать только способы входа, включённые в установке: GitHub и Google — если задано их
OAuth-приложение, корпоративных провайдеров — по их настройкам, «Продолжить без входа» — если гостевой вход включён.
Список SHALL отдавать `GET /api/auth/providers` без входа. Без единого способа входа страница SHALL сообщать, что вход
не настроен.

#### Scenario: Только корпоративный вход

- **WHEN** оператор задал только корпоративного провайдера и выключил гостевой вход
- **THEN** на странице входа одна кнопка «Войти через <название провайдера>», без GitHub, Google и «Продолжить без
  входа»

#### Scenario: Список способов входа

- **WHEN** клиент без сеанса запрашивает `GET /api/auth/providers`
- **THEN** ответ имеет статус 200 и содержит включённых провайдеров с идентификаторами и названиями и признак
  гостевого входа

#### Scenario: Вход не настроен

- **WHEN** в установке нет ни одного провайдера, а гостевой вход выключен
- **THEN** страница входа сообщает «Вход не настроен. Обратитесь к администратору»

### Requirement: Выключение гостевого входа

Оператор SHALL мочь выключить гостевой вход. Тогда запрос «Продолжить без входа» SHALL получать статус 403, и гость
не создаётся; действующие гостевые сеансы продолжают работать до истечения, а уборка брошенных гостей продолжается.

#### Scenario: Гостевой вход выключен

- **WHEN** гостевой вход выключен, и клиент без сеанса отправляет `POST /api/guest`
- **THEN** ответ имеет статус 403, и гость не создаётся

### Requirement: Вход заблокированного пользователя

Пользователь, которого заблокировал администратор, SHALL NOT входить: вход через GitHub, Google или корпоративного
провайдера SHALL вести на страницу входа с `?blocked`, где сказано «Учётная запись заблокирована администратором
установки», а тестовый вход — отвечать 403. Учётная запись при этом SHALL NOT меняться, кроме имени и аватара от
провайдера.

#### Scenario: Вход через провайдера

- **WHEN** заблокированная Алиса входит через GitHub
- **THEN** сеанс не создаётся, и открывается страница входа с сообщением о блокировке

#### Scenario: Вход через корпоративного провайдера

- **WHEN** заблокированный пользователь входит через Keycloak компании
- **THEN** сеанс не создаётся, и открывается страница входа с сообщением о блокировке

#### Scenario: Вход после разблокировки

- **WHEN** администратор разблокировал Алису, и она входит через GitHub
- **THEN** она входит, как раньше, со своими досками

### Requirement: Признак администратора в профиле

Профиль текущего пользователя `GET /api/me` SHALL содержать `admin`: `true` для администратора установки, `false` для
остальных, в том числе для гостей.

#### Scenario: Профиль администратора

- **WHEN** администратор запрашивает `/api/me`
- **THEN** ответ содержит `admin: true`
