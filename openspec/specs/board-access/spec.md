# board-access Specification

## Purpose

Определяет, кому принадлежит доска и кто может открыть её через API и подключиться к её документу
в реальном времени: доску открывает по ссылке любой пользователь, вошедший в систему или работающий гостем, а
участники, которым владелец дал личную роль напрямую или ссылкой-приглашением, — и при закрытой ссылке.

## Requirements

### Requirement: Владелец доски

Пользователь, создавший доску, SHALL становиться её владельцем.

#### Scenario: Создание доски

- **WHEN** аутентифицированный пользователь создаёт доску
- **THEN** он становится её владельцем, и доска появляется в его списке досок

### Requirement: Доступ к доске по ссылке

Любой аутентифицированный пользователь, в том числе гость, SHALL получать доску по её идентификатору, то есть
открывать её по ссылке, если его роль на доске — с учётом режима доступа по ссылке `view` или `edit` и личной роли
участника — не пустая; владелец получает свою доску при любом режиме, участник — при любом режиме со своей ролью. Если
роли нет, например режим — `none`, а пользователь не участник, запрос SHALL получать статус 403. Доска, которой не
существует, SHALL получать статус 404.

#### Scenario: Открытие доски другого пользователя по ссылке

- **WHEN** пользователь B открывает ссылку на доску пользователя A с режимом `edit`
- **THEN** `GET /api/boards/{id}` отвечает статусом 200, и B редактирует доску вместе с A, а в списке досок
  B этой доски нет

#### Scenario: Доска с закрытым доступом по ссылке

- **WHEN** пользователь B, не участник, запрашивает `GET /api/boards/{id}` доски пользователя A с режимом `none`
- **THEN** ответ имеет статус 403, а A получает свою доску со статусом 200

#### Scenario: Участник при закрытой ссылке

- **WHEN** участник B с ролью `viewer` запрашивает `GET /api/boards/{id}` доски с режимом `none`
- **THEN** ответ имеет статус 200 и содержит `role` = `viewer`

#### Scenario: Несуществующая доска

- **WHEN** пользователь запрашивает `GET /api/boards/{id}` доски, которой нет
- **THEN** ответ имеет статус 404

### Requirement: Токен доступа к синхронизации

Система SHALL выдавать аутентифицированному пользователю по запросу `POST /api/boards/{id}/collab-token` токен
доступа к документу существующей доски сроком не больше 5 минут. Пользователь без роли на доске — не владелец и не
участник при режиме `none` — SHALL получать статус 403, и токен не выдаётся.

#### Scenario: Токен для доски

- **WHEN** пользователь запрашивает токен для своей доски или для доски, открытой по ссылке
- **THEN** ответ имеет статус 200 и содержит токен, срок действия которого истекает не позже чем через
  5 минут

#### Scenario: Токен для доски, открытой для просмотра

- **WHEN** участник по ссылке запрашивает токен для доски с режимом `view`
- **THEN** ответ имеет статус 200 и содержит токен

#### Scenario: Токен для доски с закрытым доступом

- **WHEN** не владелец и не участник запрашивает токен для доски с режимом `none`
- **THEN** ответ имеет статус 403, и токен не выдаётся

#### Scenario: Токен участника при закрытой ссылке

- **WHEN** участник доски с режимом `none` запрашивает токен
- **THEN** ответ имеет статус 200 и содержит токен

#### Scenario: Токен для несуществующей доски

- **WHEN** пользователь запрашивает токен для доски, которой нет
- **THEN** ответ имеет статус 404, и токен не выдаётся

### Requirement: Подключение к синхронизации только с токеном

Сервис синхронизации SHALL принимать подключение к документу доски только с действительным токеном,
выданным для этой доски, и отклонять остальные подключения.

#### Scenario: Подключение без токена или с просроченным токеном

- **WHEN** клиент подключается к документу доски без токена, с просроченным токеном или с токеном
  с неверной подписью
- **THEN** соединение отклоняется, и клиент не получает содержимое документа

#### Scenario: Токен для другой доски

- **WHEN** клиент подключается к документу доски X с токеном, выданным для доски Y
- **THEN** соединение отклоняется

#### Scenario: Переподключение после истечения токена

- **WHEN** соединение владельца прервалось, и его прежний токен истёк
- **THEN** клиент сам получает новый токен и переподключается без действий пользователя

### Requirement: Режим доступа по ссылке

У доски SHALL быть режим доступа по ссылке: `none` — доску открывает только владелец, `view` — по ссылке её смотрят
без правки, `public` — по ссылке её смотрят без правки и без входа, `edit` — по ссылке её редактируют. Новая доска SHALL
получать режим `edit`. Владелец SHALL менять режим запросом `PATCH /api/boards/{id}` с полем `linkAccess`; смена режима
не меняет время последнего изменения доски.

#### Scenario: Владелец закрывает доступ

- **WHEN** владелец отправляет `PATCH /api/boards/{id}` с телом `{"linkAccess": "none"}`
- **THEN** ответ имеет статус 200 и содержит `linkAccess` = `none`, а `updatedAt` доски не меняется

#### Scenario: Владелец открывает доску без входа

- **WHEN** владелец отправляет `PATCH /api/boards/{id}` с телом `{"linkAccess": "public"}`
- **THEN** ответ имеет статус 200 и содержит `linkAccess` = `public`

#### Scenario: Режим новой доски

- **WHEN** пользователь создаёт доску
- **THEN** ответ содержит `linkAccess` = `edit`

#### Scenario: Неизвестный режим

- **WHEN** владелец отправляет `PATCH /api/boards/{id}` с телом `{"linkAccess": "comment"}`
- **THEN** ответ имеет статус 400, и режим доски не меняется

#### Scenario: Сменить режим пытается не владелец

- **WHEN** пользователь B, открывший доску пользователя A по ссылке, отправляет `PATCH /api/boards/{id}` с полем
  `linkAccess`
- **THEN** ответ имеет статус 403, и режим доски не меняется

### Requirement: Просмотр без правки

Сервис синхронизации SHALL не применять и не рассылать изменения документа, которые пришли по соединению с правом
`view`, а участникам с таким правом SHALL доставлять изменения остальных, как обычно. Их курсоры и выделения SHALL
видеть остальные участники. Страница доски SHALL показывать такому участнику доску без средств правки.

#### Scenario: Изменение по соединению только для чтения

- **WHEN** клиент с токеном с правом `view` отправляет изменение документа
- **THEN** документ на сервере не меняется, и остальные участники изменения не получают

#### Scenario: Участник смотрит доску

- **WHEN** пользователь B открывает доску пользователя A с режимом `view`, и A добавляет фигуру
- **THEN** B видит новую фигуру и отметку «Только просмотр», может прокручивать, масштабировать, выделять
  и копировать фигуры, а панели фигур, инструментов правки, правки страниц и импорта у B нет

### Requirement: Право доступа при подключении

Сервис синхронизации SHALL определять право пользователя на документ доски при каждом подключении по его текущей роли
на доске, а не по той, что была при выдаче токена: роль `owner` или `editor` SHALL давать право правки, `viewer` —
право просмотра. Подключение пользователя без роли SHALL отклоняться, и из документа ему ничего не отправляется.
Страница доски SHALL предлагать средства правки только по соединению, которое принимает изменения.

#### Scenario: Режим сменился после выдачи токена

- **WHEN** участник B получил токен при режиме `edit`, A сменил режим на `view`, и затем B подключается с этим
  токеном
- **THEN** соединение B только для чтения, и его изменения не доходят до документа и до A

#### Scenario: Доступ закрыт до подключения

- **WHEN** участник B получил токен при режиме `edit`, A сменил режим на `none`, и затем B подключается с этим
  токеном
- **THEN** подключение отклоняется, B не получает документа и видит «Нет доступа»

#### Scenario: Владелец при закрытом доступе

- **WHEN** владелец подключается к своей доске с режимом `none`
- **THEN** соединение принимает его изменения

#### Scenario: Участник с правкой при закрытом доступе

- **WHEN** участник с ролью `editor` подключается к доске с режимом `none`
- **THEN** соединение принимает его изменения, а соединение участника с ролью `viewer` — только для чтения

### Requirement: Смена режима у подключённых участников

Когда владелец сменил режим доступа, роль участника, убрал участника или передал владение на странице доски,
подключённые к ней пользователи SHALL получать права своей новой роли без перезагрузки страницы. Если это сделали
иначе, например запросом к API без открытой доски, права новой роли SHALL доходить до подключённых не позже чем через
минуту. Пользователь, у которого роли не осталось, SHALL видеть «Нет доступа», а правки, которые он отправит после
смены, SHALL не применяться.

#### Scenario: Правка становится просмотром

- **WHEN** участник B редактирует доску пользователя A, и A меняет режим на `view`
- **THEN** у B пропадают средства правки и появляется отметка «Только просмотр», а соединение B переходит
  в режим только для чтения

#### Scenario: Доступ закрыт

- **WHEN** участник B работает на доске пользователя A, и A меняет режим на `none`
- **THEN** B видит «Нет доступа», и его соединение с документом закрывается

#### Scenario: Просмотр становится правкой

- **WHEN** участник B смотрит доску с режимом `view`, и A меняет режим на `edit`
- **THEN** у B появляются средства правки, и его изменения доходят до A

#### Scenario: Режим сменён без страницы доски

- **WHEN** участник B работает на доске пользователя A, и A меняет режим на `none` запросом к API, не открывая
  доску
- **THEN** не позже чем через минуту B видит «Нет доступа», и его соединение с документом закрывается

#### Scenario: Роль участника становится просмотром

- **WHEN** участник B с ролью `editor` правит доску с режимом `none`, и владелец в окне «Поделиться» меняет его роль
  на «Просмотр»
- **THEN** у B без перезагрузки появляется отметка «Только просмотр», а его соединение переходит в режим только для
  чтения

#### Scenario: Владение передано

- **WHEN** владелец A на открытой доске делает владельцем участника B
- **THEN** B без перезагрузки получает средства владельца — режим ссылки, участников, переименование, — а A остаётся
  на доске редактором

### Requirement: Окно «Поделиться»

Страница доски SHALL показывать кнопку «Поделиться», которая открывает ссылку на доску с текущей страницей
и кнопку «Копировать», копирующую ссылку в буфер обмена. Владелец SHALL видеть в этом окне режим доступа
и менять его выбором «Только я», «Просмотр», «Все, у кого есть ссылка, без входа» или «Редактирование»; остальные
участники видят свой уровень доступа. В режиме `public` окно SHALL показывать всем участникам код `<iframe>` просмотра
доски `/view/{id}` с текущей страницей и кнопку «Копировать код».

#### Scenario: Копирование ссылки

- **WHEN** участник нажимает «Поделиться», затем «Копировать»
- **THEN** в буфере обмена — адрес доски с её текущей страницей, а кнопка сообщает, что ссылка скопирована

#### Scenario: Владелец меняет режим

- **WHEN** владелец выбирает «Просмотр» в окне «Поделиться»
- **THEN** режим доски становится `view`, и окно показывает выбранный режим

#### Scenario: Окно у участника по ссылке

- **WHEN** участник по ссылке открывает окно «Поделиться» доски с режимом `view`
- **THEN** он видит ссылку и то, что по ссылке доску можно только смотреть, но не может сменить режим

#### Scenario: Код для встраивания

- **WHEN** владелец выбирает «Все, у кого есть ссылка, без входа» и нажимает «Копировать код»
- **THEN** режим доски становится `public`, а в буфере обмена — `<iframe>` с адресом `/view/{id}?page=…` текущей
  страницы

### Requirement: Участники доски

Владелец SHALL давать пользователю личную роль на своей доске — `editor` («Редактирование») или `viewer`
(«Просмотр»), — и такой пользователь SHALL становиться участником доски. Владелец SHALL не быть участником своей
доски. Участие SHALL удаляться вместе с доской и с пользователем.

#### Scenario: Участник с ролью

- **WHEN** владелец A дал пользователю B роль `editor` на доске X
- **THEN** B — участник X с ролью `editor`, а при удалении X его участие удаляется вместе с ней

### Requirement: Роль на доске

Роль пользователя на личной доске SHALL быть `owner` для владельца, а для остальных — большей из личной роли участника
и роли, которую даёт режим ссылки (`edit` — `editor`, `view` и `public` — `viewer`, `none` — никакой); роли упорядочены
от `viewer` к `editor` и `owner`. На доске пространства к ним SHALL добавляться роль, которую даёт пространство, по
требованию «Наследуемые права на доске пространства», а `owner` SHALL получать и ответственный владелец доски, и
владельцы и администраторы пространства. Пользователь без роли SHALL не получать доску, как при закрытой ссылке.

#### Scenario: Личная роль больше ссылки

- **WHEN** у доски режим `none`, а B — её участник с ролью `editor`
- **THEN** роль B на доске — `editor`, и B правит доску

#### Scenario: Ссылка больше личной роли

- **WHEN** у доски режим `edit`, а B — её участник с ролью `viewer`
- **THEN** роль B на доске — `editor`

#### Scenario: Ссылка закрыта, участник смотрит

- **WHEN** у доски режим `none`, а B — её участник с ролью `viewer`
- **THEN** роль B — `viewer`, и B смотрит доску без правки

#### Scenario: Доска открыта без входа

- **WHEN** у доски режим `public`, B — вошедший пользователь, не участник, а C — её участник с ролью `editor`
- **THEN** роль B — `viewer`, и соединение B с документом только для чтения, а C правит доску

#### Scenario: Роль из пространства больше ссылки

- **WHEN** у доски пространства режим ссылки `view`, `workspaceAccess` — `edit`, а B — редактор пространства
- **THEN** роль B — `editor`

### Requirement: Список участников

Любой пользователь с ролью на доске SHALL получать по запросу `GET /api/boards/{id}/members` владельца первым и
затем участников в порядке присоединения, у каждого — `id`, `name`, `avatarUrl` и `role` (`owner` у владельца, у
участника — его личная роль). Пользователь без роли SHALL получать статус 403.

#### Scenario: Участник смотрит список

- **WHEN** B, участник доски пользователя A с ролью `viewer`, запрашивает список участников
- **THEN** ответ имеет статус 200: A с `role` = `owner`, затем B с `role` = `viewer`

### Requirement: Управление участниками

Пользователь с ролью `owner` на доске SHALL менять роль участника запросом `PUT /api/boards/{id}/members/{userId}` с
телом `{"role": …}`, тем же запросом добавлять участником того, кто открывал доску по ссылке, а на доске пространства —
и любого участника пространства, и убирать участника запросом `DELETE /api/boards/{id}/members/{userId}`. Пользователь,
которого так добавить нельзя, SHALL получать статус 404, а запрос пользователя без роли `owner` — 403.

#### Scenario: Смена роли

- **WHEN** владелец отправляет `PUT /api/boards/{id}/members/{B}` с телом `{"role": "viewer"}` для участника B
  с ролью `editor`
- **THEN** ответ имеет статус 200, и роль B — `viewer`

#### Scenario: Открывавший по ссылке становится участником

- **WHEN** B открывал доску по ссылке, и владелец отправляет `PUT /api/boards/{id}/members/{B}` с телом
  `{"role": "editor"}`
- **THEN** B — участник с ролью `editor`

#### Scenario: Посторонний пользователь

- **WHEN** владелец отправляет `PUT /api/boards/{id}/members/{C}` для пользователя C, который доску не открывал и не
  участник её пространства
- **THEN** ответ имеет статус 404, и C не становится участником

#### Scenario: Участник убран

- **WHEN** владелец убирает участника B с ролью `editor` с доски с режимом `none`
- **THEN** B больше не участник и получает на запрос доски статус 403

#### Scenario: Управляет не владелец

- **WHEN** участник с ролью `editor` пытается изменить роль другого участника или убрать его
- **THEN** ответ имеет статус 403, и участники не меняются

### Requirement: Открывавшие доску по ссылке

Владелец SHALL получать по запросу `GET /api/boards/{id}/visitors` пользователей, которые открывали доску по ссылке и
не стали участниками, недавно открывавших первыми, не больше 50. Остальные SHALL получать статус 403.

#### Scenario: Кого добавить

- **WHEN** B и C открывали доску по ссылке, а C уже участник
- **THEN** владелец получает в списке B, но не C

### Requirement: Ссылки-приглашения

Владелец SHALL создавать ссылку-приглашение с ролью `editor` или `viewer` запросом `POST /api/boards/{id}/invites`,
получать действующие приглашения запросом `GET /api/boards/{id}/invites` — у каждого адрес `/invite/<токен>`, роль и
время создания — и отзывать их запросом `DELETE /api/boards/{id}/invites/{inviteId}`. Токен SHALL быть случайным, не
короче 128 бит. Остальные SHALL получать статус 403.

#### Scenario: Создание приглашения

- **WHEN** владелец отправляет `POST /api/boards/{id}/invites` с телом `{"role": "editor"}`
- **THEN** ответ имеет статус 201 и содержит адрес вида `/invite/<токен>` и роль `editor`, и приглашение есть в
  списке приглашений доски

#### Scenario: Приглашения видит только владелец

- **WHEN** участник с ролью `editor` запрашивает приглашения доски или создаёт приглашение
- **THEN** ответ имеет статус 403

### Requirement: Принятие приглашения

Любой вошедший пользователь, в том числе гость, SHALL принимать приглашение запросом
`POST /api/invites/{token}/accept`: он становится участником с ролью приглашения, а участник с меньшей ролью получает
роль приглашения, с большей — сохраняет свою. Владелец доски SHALL оставаться владельцем. Ответ SHALL содержать доску
с ролью принявшего; отозванное или неизвестное приглашение SHALL получать статус 404.

#### Scenario: Приглашение на правку

- **WHEN** у доски режим `none`, и B принимает приглашение с ролью `editor`
- **THEN** ответ имеет статус 200 и содержит доску с `role` = `editor`, и B правит доску

#### Scenario: Меньшая роль не отнимает большую

- **WHEN** B — участник с ролью `editor` и принимает приглашение с ролью `viewer`
- **THEN** роль B остаётся `editor`

#### Scenario: Отозванное приглашение

- **WHEN** владелец отозвал приглашение, и C пытается его принять
- **THEN** ответ имеет статус 404, и C не становится участником, а B, принявший его раньше, остаётся участником

### Requirement: Страница приглашения

Адрес `/invite/<токен>` SHALL принимать приглашение и открывать доску. Посетителя без сеанса SHALL отправлять на
страницу входа, а «Продолжить без входа» SHALL возвращать его на приглашение. Отозванное или неизвестное
приглашение SHALL показывать «Приглашение недействительно».

#### Scenario: Гость по приглашению

- **WHEN** посетитель без сеанса открывает ссылку-приглашение и нажимает «Продолжить без входа»
- **THEN** он становится гостем, участником доски с ролью приглашения, и видит доску

#### Scenario: Недействительное приглашение

- **WHEN** пользователь открывает отозванную ссылку-приглашение
- **THEN** страница показывает «Приглашение недействительно» и ссылку на список досок

### Requirement: Передача владения

Пользователь с ролью `owner` на доске SHALL делать владельцем участника личной доски или участника пространства доски
пространства запросом `PUT /api/boards/{id}/owner` с телом `{"userId": …}`. Прежний владелец личной доски SHALL
становиться участником с ролью `editor`; прежний ответственный доски пространства сохраняет роль, которую даёт
пространство, а если она не даёт ничего — становится участником с ролью `editor`. Если у нового владельца личной доски досок столько, сколько позволяет предел личных досок, SHALL
возвращаться статус 409 с пределом в поле `limit`. Тот, кому доску так передать нельзя, SHALL давать статус 404, запрос
без роли `owner` — 403. Время изменения доски не меняется.

#### Scenario: Новый владелец

- **WHEN** владелец A делает владельцем участника B
- **THEN** доска в списке досок B, B получает `role` = `owner`, а A — участник с ролью `editor`

#### Scenario: Предел досок нового владельца

- **WHEN** у участника B уже 100 досок, и владелец пытается сделать его владельцем
- **THEN** ответ имеет статус 409 и содержит `"limit": 100`, и владелец доски не меняется

#### Scenario: Новый ответственный доски пространства

- **WHEN** администратор пространства делает ответственным за доску пространства её читателя пространства В
- **THEN** В получает на доске `role` = `owner`, а прежний ответственный — роль, которую ему даёт пространство

### Requirement: Пределы участников и приглашений

На доске SHALL быть не больше 100 участников и 20 действующих приглашений, если настройки
(`codraw.limits.members-per-board`, `codraw.limits.invites-per-board`) не задают другие пределы. Новый участник и новое
приглашение сверх предела SHALL получать статус 409 с пределом в поле `limit`, а
`codraw_limits_reached_total{limit="members"}` или `{limit="invites"}` SHALL расти.

#### Scenario: Сто первый участник

- **WHEN** на доске 100 участников, и ещё один пользователь принимает приглашение
- **THEN** ответ имеет статус 409 и содержит `"limit": 100`, и пользователь не становится участником

#### Scenario: Двадцать первое приглашение

- **WHEN** у доски 20 приглашений, и владелец создаёт ещё одно
- **THEN** ответ имеет статус 409 и содержит `"limit": 20`

### Requirement: Участники в окне «Поделиться»

Окно «Поделиться» SHALL показывать раздел «Участники»: владельца и участников доски с их ролями. Владелец SHALL
менять там роль участника («Редактирование» или «Просмотр»), убирать его («Убрать»), делать владельцем («Сделать
владельцем», с подтверждением) и добавлять открывавших доску по ссылке («Открывали по ссылке», «Добавить»), а в
разделе «Пригласить по ссылке» — создавать приглашение с ролью, копировать и отзывать его («Отозвать»). Остальные
SHALL видеть список участников без управления.

#### Scenario: Владелец приглашает

- **WHEN** владелец в разделе «Пригласить по ссылке» выбирает «Редактирование» и создаёт ссылку
- **THEN** в разделе появляется ссылка-приглашение с ролью «Редактирование» и кнопками «Копировать» и «Отозвать»

#### Scenario: Владелец добавляет открывавшего

- **WHEN** B открывал доску по ссылке, и владелец нажимает «Добавить» рядом с B
- **THEN** B появляется в разделе «Участники» с ролью «Редактирование» и пропадает из «Открывали по ссылке»

#### Scenario: Участники у не владельца

- **WHEN** участник с ролью `editor` открывает окно «Поделиться»
- **THEN** он видит владельца и участников с их ролями, но не может менять роли, убирать участников и приглашать

### Requirement: Запрос доступа

Любой вошедший пользователь, в том числе гость, SHALL просить доступ к существующей доске запросом
`PUT /api/boards/{id}/access-request` с ролью `editor` или `viewer` и необязательным сообщением владельцу не длиннее
500 символов; сообщение длиннее SHALL получать статус 400, запрос к несуществующей доске — 404. У пользователя на
доске SHALL быть не больше одного ожидающего запроса: новый запрос SHALL заменять прежний.

#### Scenario: Запрос правки при закрытой ссылке

- **WHEN** у доски режим `none`, и B, не участник, отправляет `PUT /api/boards/{id}/access-request` с телом
  `{"role": "editor", "message": "Нужно поправить схему"}`
- **THEN** ответ имеет статус 200 и содержит роль `editor` и сообщение

#### Scenario: Новый запрос заменяет прежний

- **WHEN** B просил просмотр доски и отправляет запрос правки
- **THEN** у B на доске один запрос — на правку, и владелец видит только его

#### Scenario: Слишком длинное сообщение

- **WHEN** B отправляет запрос с сообщением из 501 символа
- **THEN** ответ имеет статус 400, и запрос не сохраняется

### Requirement: Свой запрос доступа

Пользователь SHALL получать свой ожидающий запрос доступа к доске запросом `GET /api/boards/{id}/access-request` —
статус 204, когда запроса нет, — и отменять его запросом `DELETE /api/boards/{id}/access-request`.

#### Scenario: Запрос ждёт ответа

- **WHEN** B попросил правку доски и запрашивает свой запрос
- **THEN** ответ имеет статус 200 и содержит роль `editor` и сообщение B

#### Scenario: Отмена запроса

- **WHEN** B отменяет свой запрос
- **THEN** `GET /api/boards/{id}/access-request` отвечает статусом 204, и владелец запроса не видит

### Requirement: Запрос роли, которая уже есть

Запрос роли, которую пользователь на доске уже имеет или превосходит, SHALL получать статус 409 с его ролью на доске в
поле `role` и не сохраняться.

#### Scenario: Читатель просит просмотр

- **WHEN** у доски режим `view`, и B, не участник, просит роль `viewer`
- **THEN** ответ имеет статус 409 и содержит `"role": "viewer"`, и запрос не сохраняется

#### Scenario: Владелец просит доступ к своей доске

- **WHEN** владелец отправляет запрос доступа к своей доске
- **THEN** ответ имеет статус 409 и содержит `"role": "owner"`

### Requirement: Запросы доступа доски

Владелец SHALL получать по запросу `GET /api/boards/{id}/access-requests` ожидающие запросы доступа к доске, старые
первыми, у каждого — `id`, пользователь (`userId`, `name`, `avatarUrl`), `role`, `message` и `createdAt`. Остальные
SHALL получать статус 403.

#### Scenario: Владелец видит запрос

- **WHEN** B попросил правку доски с сообщением
- **THEN** владелец получает в списке запрос с именем и аватаром B, ролью `editor`, сообщением и временем

#### Scenario: Запросы видит только владелец

- **WHEN** участник с ролью `editor` запрашивает запросы доступа доски
- **THEN** ответ имеет статус 403

### Requirement: Ответ на запрос доступа

Владелец SHALL давать доступ запросом `POST /api/boards/{id}/access-requests/{requestId}/grant` с ролью `editor` или
`viewer`, не обязательно той, что просили, — пользователь становится участником с этой ролью, как при добавлении
участника, — и отклонять запрос запросом `DELETE /api/boards/{id}/access-requests/{requestId}`. Ответ SHALL удалять
запрос. Ответ на запрос, которого нет, SHALL получать статус 404, ответ не владельца — 403.

#### Scenario: Владелец даёт правку

- **WHEN** у доски режим `none`, B просил правку, и владелец даёт ему роль `editor`
- **THEN** B — участник доски с ролью `editor` и получает доску с `role` = `editor`, а запроса больше нет

#### Scenario: Владелец даёт меньше, чем просили

- **WHEN** B просил правку, а владелец даёт ему роль `viewer`
- **THEN** B — участник с ролью `viewer`, и запроса больше нет

#### Scenario: Отклонение

- **WHEN** владелец отклоняет запрос B к доске с режимом `none`
- **THEN** запроса больше нет, B получает на запрос доски статус 403 и может попросить доступ снова

#### Scenario: Запрос заменён, пока владелец отвечал

- **WHEN** владелец видел запрос B на просмотр, B заменил его запросом правки, и владелец даёт доступ по прежнему
  запросу
- **THEN** ответ имеет статус 404, и B не становится участником

#### Scenario: Отвечает не владелец

- **WHEN** участник с ролью `editor` пытается дать доступ по запросу или отклонить его
- **THEN** ответ имеет статус 403, и запрос остаётся

### Requirement: Выполненные запросы доступа

Ожидающий запрос SHALL удаляться, как только доска даёт пользователю роль, которую он просил, или большую: после
смены режима ссылки, добавления участника и смены его роли, принятия приглашения и передачи владения.

#### Scenario: Ссылка открыта для просмотра

- **WHEN** у доски режим `none`, B просил правку, C — просмотр, и владелец меняет режим на `view`
- **THEN** запрос C удаляется, а запрос B остаётся

#### Scenario: Приглашение выполнило запрос

- **WHEN** B просил просмотр и принимает приглашение доски с ролью `editor`
- **THEN** запрос B удаляется

### Requirement: Предел запросов доступа

У доски SHALL быть не больше 50 ожидающих запросов доступа, если настройка `codraw.limits.access-requests-per-board`
не задаёт другой предел. Новый запрос сверх предела SHALL получать статус 409 с пределом в поле `limit`, а
`codraw_limits_reached_total{limit="access-requests"}` SHALL расти. Замена своего запроса предел не проверяет, а ответ
владельца освобождает место.

#### Scenario: Пятьдесят первый запрос

- **WHEN** у доски 50 ожидающих запросов, и ещё один пользователь просит доступ
- **THEN** ответ имеет статус 409 и содержит `"limit": 50`, и запрос не сохраняется

#### Scenario: Замена запроса у предела

- **WHEN** у доски 50 ожидающих запросов, и один из просивших заменяет свой запрос
- **THEN** ответ имеет статус 200

### Requirement: Запросы доступа гостя

При входе гостя через провайдера его ожидающие запросы доступа SHALL переходить учётной записи; если оба просили
доступ к одной доске, SHALL оставаться более новый запрос. Запросы, которые после входа выполнены, например к доскам,
перешедшим к учётной записи от гостя, SHALL удаляться. Запросы SHALL удаляться вместе с пользователем и с доской.

#### Scenario: Гость входит

- **WHEN** учётная запись A просила просмотр доски X, а затем гость в том же браузере попросил правку X и вошёл как A
- **THEN** у A один запрос к X — на правку

#### Scenario: Ушедший гость

- **WHEN** ушедший гость просил доступ к чужой доске, и уборка гостей удаляет его
- **THEN** его запрос удаляется, а доска остаётся

### Requirement: Запрос доступа на странице доски

Страница доски, которую пользователь открыть не может, SHALL показывать «Нет доступа», выбор «Просмотр» или
«Редактирование», поле «Сообщение владельцу» и кнопку «Запросить доступ». После отправки SHALL показываться «Запрос
отправлен» и кнопка «Отменить запрос».

#### Scenario: Запрос с сообщением

- **WHEN** B на странице «Нет доступа» выбирает «Редактирование», пишет сообщение и нажимает «Запросить доступ»
- **THEN** страница показывает «Запрос отправлен» и «Отменить запрос», а владелец видит запрос B на правку с
  сообщением

#### Scenario: Отмена запроса на странице

- **WHEN** B нажимает «Отменить запрос»
- **THEN** страница снова предлагает «Запросить доступ», а владелец запроса не видит

### Requirement: Ожидание ответа на запрос доступа

Пока страница «Нет доступа» открыта, она SHALL проверять доступ время от времени и при возвращении на вкладку и
открывать доску, как только доступ появился. Если запрос пропал, а доступа нет, страница SHALL показывать «Запрос
отклонён» и снова предлагать запросить доступ.

#### Scenario: Доступ дан

- **WHEN** B на странице «Нет доступа» запросил правку, и владелец дал ему роль `editor`
- **THEN** без перезагрузки страница B открывает доску, и B её правит

#### Scenario: Запрос отклонён

- **WHEN** B на странице «Нет доступа» запросил доступ, и владелец отклонил запрос
- **THEN** страница B показывает «Запрос отклонён» и снова кнопку «Запросить доступ»

### Requirement: Запрос правки у читателя

Участник, чья роль на доске — `viewer`, SHALL видеть рядом с отметкой «Только просмотр» кнопку «Запросить правку»:
сообщение владельцу и «Отправить запрос» просят роль `editor`. Затем кнопка SHALL показывать «Запрос отправлен» с
«Отменить запрос», а если запрос отклонён, — «Запрос отклонён» с возможностью попросить снова.

#### Scenario: Правка дана

- **WHEN** читатель C запросил правку, и владелец на странице доски дал ему роль `editor`
- **THEN** без перезагрузки у C пропадает «Только просмотр» и появляются средства правки

#### Scenario: Правка не дана

- **WHEN** владелец отклонил запрос правки читателя C
- **THEN** C видит «Запрос отклонён» и остаётся читателем

### Requirement: Запросы доступа в окне «Поделиться»

Окно «Поделиться» владельца SHALL показывать раздел «Запросы доступа», когда они есть: у каждого запроса — аватар и
имя, роль, которую просят, сообщение и время, и кнопки «Дать редактирование», «Дать просмотр» и «Отклонить». Кнопка
«Поделиться» SHALL показывать владельцу число ожидающих запросов и обновлять его время от времени, при возвращении на
вкладку и при открытии окна. Остальные участники SHALL не видеть запросов.

#### Scenario: Число запросов на кнопке

- **WHEN** B попросил доступ, и владелец открывает доску
- **THEN** на кнопке «Поделиться» — «1», а в окне «Поделиться» — запрос B с ролью, сообщением и временем

#### Scenario: Ответ из окна

- **WHEN** владелец нажимает «Дать редактирование» у запроса B
- **THEN** B появляется в разделе «Участники» с ролью «Редактирование», запрос пропадает из окна, и числа на кнопке
  «Поделиться» больше нет

### Requirement: Запрет доступа по ссылке

Пока администратор держит запрет доступа по ссылке у доски, владелец SHALL NOT менять её режим ссылки на другой, чем
`none`, и включать живую картинку: `backend` отвечает 409 с `title` «Sharing blocked». Ответ доски SHALL содержать
`sharingBlocked: true`, а окно «Поделиться» SHALL показывать владельцу «Доступ по ссылке закрыт администратором
установки» и не предлагать другие режимы ссылки и живую картинку. Участники и пространство доски сохраняют свои роли.

#### Scenario: Окно «Поделиться» при запрете

- **WHEN** владелец доски с запретом открывает «Поделиться»
- **THEN** он видит, что доступ по ссылке закрыт администратором, режим «Только участники» и не может выбрать другой

#### Scenario: Смена режима через API

- **WHEN** владелец доски с запретом отправляет `PATCH /api/boards/{id}` с `{"linkAccess": "view"}`
- **THEN** ответ имеет статус 409, и режим доски остаётся `none`
